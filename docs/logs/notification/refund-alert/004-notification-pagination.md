- 시도: `GET /api/{buyer,seller}/mypage/notifications`에 page/size 파라미터 추가, 응답을 배열에서
  `{ unreadCount, totalCount, hasNext, notifications[] }` 객체로 변경(안읽음 개수는 잘린 목록과
  무관하게 서버가 직접 카운트 쿼리로 센다). 프론트는 벨 안 "더 보기"로 다음 페이지를 이어붙임.
- 결과: `./gradlew test` 전체 **382케이스 통과**(기존 379 + 신규 3).
- 증거(API 샘플, 로컬 실서버 실측): 알림 25건 중 1페이지(20건)를 전부 읽음 처리한 뒤 확인 —
  1페이지 안의 안읽은 알림 0, 서버가 준 `unreadCount` 5(안 불러온 2페이지까지 정확히 셈), 2페이지의
  실제 안읽은 알림 5. 옛 방식(프론트가 받아온 목록에서 세기)이었으면 뱃지가 0으로 사라지고 5건이
  유령처럼 남았을 상황임을 확인. 페이지 경계도 실측(1페이지 20건/hasNext=true, 2페이지 5건/
  hasNext=false, 겹침 없음).
- 참고: 검증 중 "읽음 처리 20건이 전부 안 먹는다"는 것처럼 보인 현상은 앱 버그가 아니라 zsh가
  따옴표 없는 변수를 단어 분리하지 않아 id 20개가 한 토큰으로 잘못 전송된 것이었음(응답 코드를
  직접 찍어 확인 후 확정).
