  - **추론적 평가** (코드 직접 대조):
    - `SellerRevenueSummaryRepository.incrementPaid`/`applyRefund`: 둘 다 `@Modifying` + 단일 JPQL `UPDATE ... SET col = col ± :param ... WHERE seller.id = :sellerId` 한 문장 — 애플리케이션 레벨 read-modify-write가 아니라 DB에 위임한 진짜 원자적 UPDATE. `GroupBuyTeamRepository.incrementIfCapacity`와 같은 패턴을 그대로 재사용했음을 확인.
    - `flushAutomatically=true` 버그 수정 주장 검증: `TeamDeadlineService.processDeadline()`이 `team.fail()`, `paidPayments.forEach(Payment::refund)`로 엔티티를 더티 상태로 만든 뒤 `applyRefund(...)`를 호출하는 구조를 실제 코드에서 확인. `@Modifying(flushAutomatically=true, clearAutomatically=true)`는 벌크 UPDATE 실행 **전에** `em.flush()`를 먼저 호출하므로, 그 더티 상태(team 상태 전이, payment REFUNDED 전이)가 벌크 UPDATE보다 먼저 DB에 반영된다 — 주장한 인과관계와 일치, 실제로 해결된 것으로 판단. 다만 `flushAutomatically=true`는 **그 시점의 영속성 컨텍스트 전체를 flush**하는 것이라(관련 엔티티만 골라 flush하는 게 아님) 이 두 트랜잭션(`PaymentService.create`, `TeamDeadlineService.processDeadline`)이 계속 이 호출 시점 이전에 좁은 스코프(해당 Payment/GroupBuyTeam만)만 다루는 한 부작용이 없지만, 향후 이 메서드들에 다른 미완료 변경을 추가로 넣고 그 뒤에 `incrementPaid`/`applyRefund`를 호출하는 순서로 코드가 커지면 의도치 않게 그 변경까지 조기 flush될 수 있다는 점은 잠재적 결합(coupling)으로 남아있음(현재 코드 스코프에선 결함 아님, 향후 확장 시 유의점).
    - `SellerMypageService.revenue()`가 클래스 기본 `@Transactional(readOnly = true)`를 메서드 레벨 `@Transactional`(readOnly 미지정 = false)로 오버라이드하고 있음을 코드로 확인 — 부트스트랩 INSERT(`bootstrapRevenueSummary` → `sellerRevenueSummaryRepository.save(...)`)가 readOnly 트랜잭션 안에서 조용히 무시되거나 예외가 나는 문제는 없음. `SellerRevenueSummaryTest.revenue_bootstrapsFromExistingPaymentsWhenSummaryRowMissing` 테스트가 실제로 부트스트랩 후 `findBySellerId`로 재조회해 행이 실제로 insert됐음을 검증하고 있고, 이 테스트가 통과함으로써 readOnly 오버라이드가 실제로 쓰기를 허용함을 실행 결과로도 재확인.
