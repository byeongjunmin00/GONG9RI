# 002-multi-upload — 이미지 여러 장 + 파일 업로드 + 갤러리 (로그)

## Attempt 1 — 2026-08-20 (백엔드)
- 시도: `product_image` 테이블 신규 + 업로드 엔드포인트(`POST /api/seller/products/images`) + `ProductImageStorage`(UUID 파일명, ImageIO 디코딩 판정, 긴 변 1600px 축소·JPEG 0.82 재인코딩).
- 결과: 416 케이스 통과. 업로드 테스트는 **거절 경로가 정상 경로보다 많다**(확장자만 이미지인 파일, 경로 탈출 파일명, 크기 초과).
- 겪은 문제: `src/test/resources/application.yaml`에 `app.upload.dir`을 안 넣어 컨텍스트 로딩이 깨지며 **360개 테스트가 무너졌다**. 그 파일 주석에 이미 같은 함정 경고(예전 `app.base-url` 건)가 적혀 있었는데 **두 번째로 밟았다**. 테스트 설정 파일은 메인 설정을 병합이 아니라 **대체**한다.
- 또 하나: `application.yaml`에 `app:` 키를 중복으로 쓸 뻔했다. YAML은 중복 키를 오류 없이 앞 블록을 버린다 → 커밋 전 최상위 키 중복 확인으로 막음.

## Attempt 2 — 2026-08-20 (프론트)
- 시도: 판매자 등록/수정 폼을 파일 선택으로 교체(`product-image-picker.js` 공용), 상세 페이지 갤러리(화살표·카운터·썸네일 줄).
- 설계 결정:
  - 파일 선택 시 **즉시 업로드**(폼 제출을 기다리지 않아 미리보기를 바로 보여줌), 여러 장은 **순차 업로드**(고른 순서 = 표시 순서, 첫 장이 대표).
  - 업로드만 `window.Api`가 아니라 `fetch` 직접 사용 — multipart는 브라우저가 boundary 포함 `Content-Type`을 스스로 만들어야 해서 직접 지정하면 오히려 깨진다.
  - 사진이 1장이면 화살표·카운터·썸네일을 전부 숨겨 **이전과 똑같이 보이게** 함(기존 상품 35개 호환).
- 결과: 로컬 bootRun 실측 — 파일 3장 업로드 → 상세 응답 `imageUrls`에 **순서대로**, PNG가 JPEG로 재인코딩, `imageUrls` 없이 등록한 상품도 한 장짜리로 정상 노출(하위호환).

## Attempt 3 — 2026-08-20 (용량 초과 500 버그)
- 증상: 5.5MB 사진 업로드 시 500.
- 원인: **톰캣 multipart 파서가 컨트롤러 진입 전에 거절**한다. `ProductImageStorage`의 5MB 검사는 아예 도달하지 못하고, `MaxUploadSizeExceededException`이 catch-all로 흘러 500이 됐다. 400 에러코드(`IMAGE_FILE_TOO_LARGE`)는 이미 있었는데 닿지를 못한 것.
- 해결: `GlobalExceptionHandler`에 핸들러 추가.
- 테스트 선택: **실제 톰캣을 띄운다(`RANDOM_PORT`)**. MockMvc는 multipart 파서를 타지 않아 크기 제한이 적용되지 않고, **핸들러가 없어도 통과해버려 회귀를 못 잡는다**(실제로 확인). 인증도 진짜로 해야 한다 — 비로그인은 시큐리티가 먼저 401로 끊어 파서까지 가지 않는다.
- 역검증: 핸들러를 주석 처리하면 실패, 되돌리면 통과.
