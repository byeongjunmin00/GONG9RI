## Attempt 1 (실제 OpenAI 호출 검증) — 2026-08-11 ✅ PASS

로컬에서 실제 판매자 계정으로 상품("제주 감귤 5kg", 25,000원) 등록 + 구매자 계정으로 그 상품에 공구팀 신설(1/10명 참여) 후, 같은 세션으로 4턴 실제 대화.

1. **Tool 1(상품 검색) 실호출 확인**: "감귤 관련 상품 있어? 가격도 알려줘" → "제주 감귤 5kg... 25,000원"으로 정확히 답변. `searchProducts` Tool이 실제로 호출돼 방금 등록한 실제 상품명·가격을 그대로 반영함(지어낸 값이 아님).
2. **Tool 2(내 참여 조회) 실호출 확인, 같은 세션으로 멀티턴**: "내가 지금 참여중인 공구팀 있어? 몇 명 모였는지도 알려줘" → "제주 감귤 5kg... 1명 참여... 최대 10명... 마감일은 2026년 8월 18일"로 정확히 답변(실제 DB 값과 일치). 세션ID가 이전 턴과 동일(35)하게 유지되며 두 번째 턴이 첫 번째 턴의 맥락(같은 세션) 위에서 자연스럽게 이어짐.
3. **환각 방어 확인**: 같은 세션에서 "오늘 서울 날씨 어때? 그리고 이 공구팀 판매자 전화번호 뭐야?" → "서울 날씨와 같은 GONG9RI 공동구매 서비스와 무관한 질문에는 답변할 수 없습니다. 또한, 판매자 전화번호와 관련된 정보도 제공할 수 없습니다"로 정확히 거절. 서비스 무관 질문(날씨)과 Tool로 확인 안 되는 정보(전화번호) 둘 다 지어내지 않고 정직하게 거절함 — 시스템 프롬프트의 grounding 지시가 실제로 작동함을 확인.
4. **토큰/지연 실측**: `chat_interaction_log`에 3턴 전부 성공 기록(`promptTokens` 316~443, `completionTokens` 45~84, `latencyMs` 1396~3139). `GET /api/chat/stats` → `{"model":"gpt-4o-mini","callCount":3,"totalTokens":1389,"p95LatencyMs":3139,"errorRate":0.0}`, `GET /api/buyer/chat/sessions/35/usage` → `{"sessionId":35,"totalTokens":1389}` 둘 다 실제 누적값과 정확히 일치.
5. **스트리밍 확인**: 모든 응답이 SSE `message` 이벤트로 어절 단위(OpenAI 스트리밍 토큰 단위)로 여러 번 나뉘어 도착, 마지막 청크에만 `usage`가 채워짐을 실측으로 확인(design.md에 반영). `session`/`done` 이벤트도 정확한 시점에 정확히 1회씩 도착.

## 참고 — 장애 시나리오는 실제 OpenAI 장애를 재현할 수 없어 목 테스트로 검증

발제가 요구하는 "장애 시나리오 테스트"는 실제 API 호출로는 타임아웃/RateLimit/5xx를 임의로 재현할 수 없으므로, `BuyerChatServiceTest`에서 `Flux.error(new TimeoutException(...))`/`Flux.error(mock(RateLimitException.class))`/`Flux.error(new RuntimeException(...))`를 직접 흘려보내 각각 `ChatErrorType.TIMEOUT`/`RATE_LIMIT`/`OTHER`로 정확히 분류·기록되는지 검증함(3케이스 전부 통과). 실제 15초 타임아웃을 기다리는 대신 예외 자체를 주입해서 분류 로직만 빠르게 검증하는 방식 — Reactor의 실제 타임아웃 메커니즘 자체는 라이브러리 표준 기능이라 재검증 대상이 아님.

## Attempt 2 (RAG 결합) — 2026-08-11 ✅ PASS

전용운이 `ai/policy-rag`(`PolicyRagService.findRelevantSnippets(query)`, 정책 문서 검색 전용, REST 없이 인터페이스+생성자 주입)를 완료해 커밋했고, 사용자 확인 후 `BuyerChatService`에 실제로 연결함(발제 도전 "RAG+Tool Calling 결합").

- **연결**: `streamChat()`에서 세션/이력 조회와 같은 시점(스트림 시작 전, 동기)에 `policyRagService.findRelevantSnippets(request.content())` 호출 → 시스템 프롬프트 뒤에 "질문과 관련이 없으면 참고하지 말고 무시해라"는 지시와 함께 스니펫을 덧붙임. `try/catch`로 감싸서 RAG 검색 실패가 챗봇 턴 전체를 실패시키지 않게 함(RAG는 부가 기능).
- **테스트**: `BuyerChatServiceTest`에 `@MockitoBean PolicyRagService` 추가 후 2케이스 신규 — (1) RAG 스니펫이 있으면 무시 지시와 함께 시스템 프롬프트에 포함되는지, (2) RAG 검색이 예외를 던져도 챗봇 턴은 정상 성공하는지. `./gradlew build` 전체 136케이스(134 + 신규 2) 통과, 회귀 없음.
- **실제 OpenAI 호출로 첫 검증에서 프롬프트 결함 발견·수정**: "제 돈은 언제 돌려받을 수 있나요?"(`ai/policy-rag` Attempt 2에서 raw score가 낮아 힘들어했던 패러프레이즈) 질문에 정확한 RAG 스니펫(환불 트리거 규칙)이 실제로 전달됐는데도, 모델이 "정확한 정보는 확인할 수 없습니다"로 불필요하게 얼버무림. 원인: 기존 시스템 프롬프트의 "도구로 확인하지 않은 사실을 추측해서 답하지 마라"는 지시가 RAG로 확인된 정책 정보까지 "확인 안 된 것"으로 취급하게 만든 것. 프롬프트에 "아래 제공되는 정책 문서 스니펫은 이미 확인된 사실이니 망설이지 말고 답변 근거로 사용해라"를 추가해서 해결.
- **수정 후 재검증**: 같은 질문 재호출 → "공구 기한이 지나면 자동으로 실패 처리 및 환불이 진행됩니다"로 정확하고 확신 있게 답변(더 이상 불필요한 얼버무림 없음, 정확한 시점은 확인 불가라는 정직한 캐비엇만 남음 — 실제로 스케줄러 주기에 따라 달라지므로 타당한 캐비엇). 서비스 무관 질문(날씨) 거절도 회귀 없이 그대로 유지됨.
- 테스트 데이터(구매자 계정 1개, 정책 색인 6청크 — 인메모리라 자동 소멸) 정리 완료.

## Attempt 3 (재점검 — 실제 재현 검증 2건 보강) — 2026-08-11 ✅ PASS

전체 프로젝트 재점검 중, AI 필수2·RAG 도전 항목에서 "근거는 있지만 실제로 검증한 적은 없는" 항목 2개를 발견해서 실제 OpenAI 호출로 보강.

1. **Tool 호출 실패 시 자연어 안내 — 실제 재현**: 지금까지 `DefaultToolExecutionExceptionProcessor`의 기본 동작을 jar 디컴파일 근거로만 설명하고 실제로 예외를 발생시켜본 적이 없었음(design.md에 스스로 "실제 재현 테스트는 안 함"이라고 적어뒀던 부분). `ChatbotTools.searchProducts`에 특정 키워드("TEMP_TOOL_FAILURE_TEST")로만 발동하는 임시 예외 트리거를 추가 → 실제 호출로 "이 키워드로 검색해줘"라고 요청 → LLM이 도구 실패를 감지하고 "현재 상품 검색 서비스에 일시적인 장애가 발생하여 상품을 검색할 수 없습니다. 잠시 후 다시 시도해주시기 바랍니다."로 자연어 응답. SSE 스트림은 `onError`(내 장애격리 폴백 경로)가 아니라 정상 `onComplete`로 흘렀고, `chat_interaction_log`에도 `success=true`로 기록됨(도구 하나가 실패해도 LLM이 그 정보를 받아 자연스럽게 대화를 이어간 것이지, 대화 자체가 실패한 게 아니라는 뜻) — 검증 후 임시 트리거 코드는 즉시 제거.
2. **RAG 출처표시 — 누락 발견 후 보강**: 시스템 프롬프트에 "답변에 정책 스니펫을 썼으면 출처를 밝혀라"는 지시 자체가 없었음(design.md·구현 어디에도 없었음, 재점검 중 처음 발견). `buildSystemPrompt`에 "관련이 있어서 답변에 사용했다면 각 스니펫 맨 앞의 '# 문서 제목'을 답변 끝에 '(출처: 문서 제목)' 형식으로 밝혀라" 지시 추가. 실제 호출로 검증: "환불은 언제 되나요?" → 답변 끝에 정확히 "(출처: 공구팀 실패(미성사) 및 환불 트리거)"가 붙어서 나옴.
3. `BuyerChatServiceTest`의 기존 RAG 프롬프트 테스트에 출처 지시 포함 여부(`assertTrue(systemPrompt.contains("출처"))`) 검증 추가. `./gradlew clean build` 136케이스 전부 통과(테스트 개수는 문항 추가가 아니라 기존 테스트 강화라 그대로), 임시 검증 계정·세션 데이터 정리 완료.

## Attempt 4 (RAG 출처표시 — 내부 문서 제목 노출 문제 발견·수정) — 2026-08-11 ✅ PASS

Attempt 3에서 넣은 출처표시가 정책 문서의 **내부 관리용 제목**("공구팀 실패(미성사) 및 환불 트리거")을 그대로 구매자에게 노출하고 있다는 지적을 받음 — "미성사", "트리거" 같은 표현이 고객 응대에 어울리지 않음(정보 유출은 아니지만 말투가 어색함).

- **테스트**: `PolicyDocumentIndexerTest`(신규, 스프링 컨텍스트 없는 순수 단위 테스트) — 각 청크가 내부 제목과 표시용 출처명을 모두 포함하는지 검증. 기존 `BuyerChatServiceTest`의 출처 지시 검증(`contains("출처")`)은 문구가 바뀌어도 그대로 통과.
