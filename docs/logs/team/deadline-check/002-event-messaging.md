## Attempt 1 — 2026-08-10
- 시도: `TeamDeadlineScheduler.checkDeadlines()`가 스캔한 팀 id마다 `teamDeadlineService.processDeadline(teamId)`를 직접 호출하던 것을, `ApplicationEventPublisher.publishEvent(new TeamDeadlineDetectedEvent(teamId))` 발행으로 교체(스케줄러는 스캔+발행만, 처리 로직 직접 호출 제거).
  - 신규 `event/TeamDeadlineDetectedEvent`(record, teamId만) — 마감 감지 이벤트.
  - 신규 `event/TeamDeadlineEventListener`(`@Component`) — `@EventListener` + `@Async`로 이 이벤트를 구독해 기존 `TeamDeadlineService.processDeadline(teamId)`를 그대로 호출. 락·재검증 로직은 전혀 안 바꿈(`docs/dev/team/deadline-check/design.md`에 있는 그대로) — 진입 경로만 이벤트로 바뀜.
  - `@Async`를 쓴 이유: `eventPublisher.publishEvent(...)`는 기본적으로 동기 호출이라, 리스너에 `@Async`가 없으면 스케줄러의 for 루프가 각 팀의 락 대기+DB 쓰기를 그 자리에서 기다리게 돼 "스캔 루프를 막지 않아야 한다"(태스크 7)를 못 지킨다. 신규 `config/AsyncConfig`(`@EnableAsync` + `ThreadPoolTaskExecutor` 빈, core=2/max=10/queue=100 — 기본 `SimpleAsyncTaskExecutor`의 무제한 스레드 생성 대신 작은 풀로 제한) + `AsyncUncaughtExceptionHandler`(예외를 삼키지 않고 SLF4J ERROR로 로그, `docs/code-convention.md` 로깅 규칙).
  - 환불 완료 이벤트(`event/TeamRefundedEvent`: teamId, sellerId, buyerMemberIds)를 `TeamDeadlineService.processDeadline()` 안에서 환불 실제로 발생한 경우(`!paidPayments.isEmpty()`)에만 `eventPublisher.publishEvent(...)`로 발행 — 이 메서드가 이미 `@Transactional`이라 발행 시점에 활성 트랜잭션이 있다. 소비자(`event/TeamRefundedEventListener`)는 `@TransactionalEventListener(phase = AFTER_COMMIT)`로 구독해, 이 트랜잭션이 실제로 커밋된 뒤에만 반응하게 함(계획이 명시한 "커밋 전/롤백 시 발행되면 안 됨" 요구를 정확히 이 애노테이션으로 충족). 이 리스너는 `@Async`를 붙이지 않음 — 어차피 원본 트랜잭션(`processDeadline`)이 이미 비동기 스레드(`TeamDeadlineEventListener`) 위에서 실행 중이라, "스캔 루프를 막지 않는다"는 요구사항은 이미 충족돼 있고, 동기로 두는 게 테스트를 훨씬 결정적으로 만듦(뒤에 별도 스레드 대기 불필요).
- 기존 `TeamDeadlineServiceTest`(5케이스)는 전부 그대로 `teamDeadlineService.processDeadline(teamId)`를 직접 호출하는 방식을 유지 — `processDeadline` 자체의 시그니처/로직은 안 바꿨고(끝에 이벤트 발행만 추가) 이 5케이스는 회귀 없이 그대로 통과.
- 신규 `scheduler/TeamDeadlineSchedulerTest`(Mockito 순수 단위 테스트, Spring 컨텍스트/DB 없음) — `checkDeadlines()`가 스캔된 각 팀 id로 `TeamDeadlineDetectedEvent`만 발행하고 `teamDeadlineService.processDeadline()`을 직접 호출하지 않는지 검증(태스크 1 정확히 이 부분). DB 락 경합 문제를 피하려고 일부러 `@SpringBootTest` 대신 순수 Mockito로 작성.
- 신규 `event/TeamDeadlineEventFlowTest`(`@SpringBootTest`, 클래스 레벨 `@Transactional` 안 씀) — (a) `TeamDeadlineDetectedEvent`를 실제로 발행하면 비동기 리스너가 상태전환+환불을 수행하는지(폴링으로 5초 대기), (c) `processDeadline`을 직접 호출(실제 커밋 발생)하면 구매자 전원+판매자에게 알림이 생성되는지. (b, 롤백 시 알림 미생성)는 `TeamDeadlineServiceTest`에 추가한 케이스로 커버(아래 로그의 "환불이 발생해도 트랜잭션이 커밋되지 않으면..." 참고) — 클래스 레벨 `@Transactional`(테스트 종료 시 항상 롤백)을 그대로 이용하면 AFTER_COMMIT 리스너가 절대 실행되지 않는다는 걸 보이는 게 가장 직접적이라고 판단.
  - `@Transactional`을 안 쓴 이유: (a)는 `TeamDeadlineEventListener`가 `@Async`라 별도 스레드에서 `findByIdForUpdate`(비관적 락, `SELECT ... FOR UPDATE`)로 팀을 다시 읽는데, 테스트 스레드가 트랜잭션을 열어둔 채면(같은 팀 row에 대한 INSERT가 아직 커밋 안 됨) 그 SELECT FOR UPDATE가 테스트 롤백 전까지 블로킹된다. (c)는 원래도 AFTER_COMMIT이 "진짜 커밋"에 반응하는지를 보는 테스트라 실제 커밋이 필요. `SellerRevenueSummaryConcurrencyTest`와 같은 패턴으로 `@AfterEach`에서 직접 정리(멤버id 기준으로 알림을 다시 조회해서 지움 — 비동기로 늦게 생성돼도 누락 없이 정리됨).
- 막힌 지점(발견 즉시 수정, 재시도 아님): 처음엔 `NotificationService.createTeamRefundedNotifications`에 평범한 `@Transactional`(REQUIRED)만 붙였는데, (a)/(c) 테스트가 "알림 0건"으로 실패함(로그엔 "생성 완료"가 찍히는데 실제 INSERT SQL은 전혀 안 나가고 DB에도 없음). 원인은 스프링 공식 문서가 명시하는 `@TransactionalEventListener` 캐비앗 — AFTER_COMMIT 콜백 시점엔 원본 트랜잭션의 리소스(ConnectionHolder)가 스레드에서 아직 완전히 정리되지 않을 수 있어, 기본 propagation(REQUIRED)으로 두면 새 트랜잭션을 시작하는 대신 "이미 물리적으로 커밋된" 그 리소스에 조인해버려 이 메서드의 쓰기가 커밋되지 않고 사라짐. `@Transactional(propagation = Propagation.REQUIRES_NEW)`로 바꿔서 해결 — 이후 (a)/(c) 전부 통과.
- 환경: 이 샌드박스에 로컬 MySQL 서비스가 등록/기동돼 있지 않아(`netstat` 3306 리스닝 없음, Windows 서비스 없음) 직접 `mysqld.exe --initialize-insecure` + `--no-defaults`(경로에 한글 사용자명이 섞인 기존 데이터 디렉터리를 쓰면 `--log-error` 옵션이 무시되고 기본 위치에 로그를 쓰려다 권한 오류로 죽는 문제가 있어, ASCII 전용 경로 `C:\mysql-test`에 새로 초기화)로 standalone 기동, `root`/`1234`로 비밀번호 설정 후 검증.
