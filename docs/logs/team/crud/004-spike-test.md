# 004-spike-test — team/join 스파이크 테스트 (실제 breaking point 탐색)

## Attempt 1 — 2026-08-06

- 목적: 002-loadtest·003-atomic-comparison에서는 VU 10/30/50으로 완만하게만 늘려서 "처리량 정체 + p95 지연 증가" 패턴까지만 봤음. 이번엔 VU를 훨씬 크게 올려서 시스템이 실제로 에러를 뱉으며 무너지는 한계점(breaking point)을 찾는다. 전략은 `lock`(기본값)만 — 003에서 lock/atomic 성능 차이가 거의 없었으므로 하나로도 결론 낼 수 있다고 판단.
- 준비: 기존 `k6/team-join-load-test.js`를 그대로 재사용(파라미터만 VU 100/200/500/1000/2000/3000로 확대). `options.thresholds`에 `checks: ['rate>0.95']` 추가해서 실행 결과 자체가 pass/fail을 보여주게 함. `maxDuration`을 60s→120s로, `setupTimeout`을 기본 60s→180s로 늘림(VU_COUNT만큼 계정을 순차 생성하는 `setup()`이 VU가 커지면 기본 타임아웃을 넘기 때문).

## Attempt 1 (Evaluate) — 2026-08-06 ✅ PASS (예상과 다른, 더 정직한 결론)

**실제로 에러가 나는 breaking point는 VU 2000까지 못 찾음** — VU 100→2000까지 6단계 전부 `checks_failed 0%`, `http_req_failed 0%`. 처음 세운 가설("VU를 계속 올리면 HikariCP 커넥션 풀 대기시간이 쌓이다가 결국 커넥션 획득 타임아웃(기본 30초)으로 에러가 터질 것")은 VU 2000(p95 19.42s, max 22.34s — 30초에 근접하지만 아직 안 넘음)까지는 확인 안 됨. VU 3000으로 더 밀어붙이면 실제로 30초를 넘겨 에러가 날 가능성이 높지만, 테스트 스크립트 자체의 준비 단계(순차 signup)가 먼저 병목이 되어 직접 확인은 못 함.

### 해석 — 억지로 "여기가 한계점"이라고 하지 않음

- **처리량은 VU와 무관하게 35~38 req/s로 완전히 평평함** — 002-loadtest에서 본 정체 패턴이 VU 2000까지도 그대로 유지됨. 이게 003에서 의심한 "HikariCP 기본 풀(10개) + 로그인 BCrypt 연산이 처리량 상한을 결정한다"는 가설과 정확히 들어맞음.
- **지연(p95)은 VU에 거의 선형으로 비례해서 늘어남**(100→904ms, 2000→19.42s, 약 20배 VU에 약 21배 지연) — 이건 "락 경합으로 무너지는 것"이 아니라 "고정된 처리 용량(초당 ~37건) 앞에 요청이 순서대로 줄 서서 기다리는" FIFO 큐잉 지연에 정확히 부합하는 패턴. 시스템이 에러 없이 **우아하게 열화(graceful degradation)**하고 있다는 뜻 — 튜터님이 물어보면 "무너진다"가 아니라 "느려지기만 하고 안 죽는다"고 정확히 답해야 함.
- **로컬 머신 한계 가능성**: 이 정도 VU(1000~2000)면 k6 자체의 스레드/소켓 자원과 로컬 머신 CPU·메모리도 같이 압박받는 상태라, "GONG9RI 서버의 한계"인지 "이 노트북+k6의 한계"인지 완전히 분리하지 못했음. 정직하게 인정할 지점.
- **진짜 breaking point(에러 급증)를 확인하려면**: (1) k6를 별도 머신에서 돌리거나, (2) `setup()`을 매 VU마다 계정을 새로 만들지 않고 미리 만들어둔 계정 풀을 재사용하도록 바꿔서 준비 단계 병목을 없애거나, (3) HikariCP 풀 크기를 늘렸을 때 처리량 상한 자체가 올라가는지 재확인하는 실험이 필요함 — 전부 이번 스코프 밖, 다음에 시간 되면 해볼 것.

### 데이터 정리

- 6단계(100/200/500/1000/2000/3000) 전부 실서버(`bootRun`)를 실제로 때린 테스트라 로컬 `gong9ri_db`에 `k6%` 접두사 실데이터가 쌓임(최종 member 7,257건 · product 7건 · group_buy_team 7건 · team_participation 3,807건). FK 순서(참여→팀→가격구간→상품→결제→회원) 지켜서 전부 삭제, `SELECT COUNT(*)`로 0건 확인함.

## Attempt 2 — 2026-08-06 (전용운) — VU=3000 실측, 실제 breaking point 확인

- 목적: Attempt 1이 VU 3000에서 `setup()`(순차 회원가입 3000회)이 180초 제한을 넘겨 측정 자체를 못 한 지점을 이어서 확인.
- 준비: 사전에 순차 signup 50회를 실측해 평균 158ms/req 확인(3000회 ≈ 474s 소요 추정). `k6/team-join-load-test.js`의 `setupTimeout`을 900s, `maxDuration`을 300s로 늘림(환경변수 `SETUP_TIMEOUT_S`/`MAX_DURATION_S`로 오버라이드 가능하게 파라미터화, 기본값만 상향 — 작은 VU 테스트에는 영향 없음, 상한값이라 실제로 그 시간을 다 쓰지 않으면 그냥 더 빨리 끝남).
- k6 미설치 상태라 winget으로 설치(`GrafanaLabs.k6`, v2.1.0). 로컬 MySQL·Redis는 Docker 컨테이너(`gong9ri-mysql`, `gong9ri-redis`)로 기동, `bootRun`으로 앱 실행.

### 결과 — VU=3000

- setup() 성공(약 8분 소요, 3000회 순차 signup 완료).
- 본 시나리오 실행 중 대량의 `dial tcp 127.0.0.1:8080: connectex: ... actively refused` 에러 발생 — **HTTP 5xx가 아니라 OS/Tomcat 소켓 accept 단계에서의 연결 거부**.
- `checks_failed`: 56.56% (3394/6000) · `http_req_failed`: 37.68% (3394/9006, setup 요청 포함 전체 기준 — 본 시나리오 6000건 중 3394건 실패한 것과 정확히 일치).
- `http_req_duration`: avg 1.93s, p90 8.36s, p95 8.86s, max 12.54s (VU=2000의 p95 19.42s보다 오히려 낮음 — 실패한 요청이 연결 거부로 빠르게 끝나버려 평균이 끌려 내려간 것, "느려짐"이 아니라 "많이 실패함"으로 양상이 바뀜).
- 처리량 43.04 req/s (실패 포함) — 기존 "35~38 req/s 평평" 패턴이 여기서 깨짐.
- **앱 프로세스 자체는 죽지 않음** — 스파이크 종료 후 `GET /api/products` 즉시 200(89ms) 응답, `TeamService`가 `currentCount=1304`까지는 정상적으로 계속 처리 중이었음(로그로 확인). 즉 애플리케이션 레벨 장애가 아니라 **Tomcat의 연결 수용 능력(기본 `acceptCount`/`maxConnections`) 한계**로 보임.

### 결론 — Attempt 1의 가설 중 하나는 틀렸고, 실제 병목은 DB 커넥션 풀이 아니라 Tomcat 연결 수용 한계

- Attempt 1의 가설("HikariCP 커넥션 획득 타임아웃(30초)으로 에러가 터질 것")은 **틀림** — p95가 오히려 VU=2000보다 낮아졌다는 것 자체가, 요청이 DB 커넥션을 기다리다 타임아웃난 게 아니라 **TCP 연결 자체가 서버에 도달하기 전에 거부**됐다는 뜻.
- 즉 VU=2000→3000 사이 어딘가에 **Tomcat이 동시에 받아들일 수 있는 연결 수 한계**가 있고, 그 이상은 요청이 애플리케이션 코드(`TeamService`, DB 등)에 도달하기도 전에 잘림. `team/join` 로직·비관적 락 자체의 한계가 아니라 **웹 서버 계층의 수용 한계**라는 뜻— 002/003의 결론("처리량 상한은 HikariCP+BCrypt")과는 다른 지점에서 발생.
- 진짜 breaking point는 **VU 2000(에러 0%)과 VU 3000(에러 37.68%) 사이**로 좁혀짐. 정확한 지점(예: 2200, 2500)을 더 좁히려면 추가 실측 필요 — 이번 스코프에서는 "3000에서는 확실히 무너진다"까지 확인.
- 로컬 머신(k6+서버 동일 머신) 한계일 가능성은 Attempt 1과 동일하게 남아있음 — 다만 앱이 안 죽고 계속 요청을 처리하고 있었다는 로그 증거로 볼 때, "k6 클라이언트 자체가 못 버틴 것"보다는 "서버가 연결을 거부한 것"에 더 가깝다고 판단.

### 데이터 정리

- VU=3000 테스트로 member 3,052건(`k6%`) + calib 계정 50건 + team_participation 1,304건 + group_buy_team 1건 + product 1건 적재됨. FK 순서(참여→팀→가격구간→상품→회원) 지켜서 전부 삭제, `SELECT COUNT(*)`로 0건 확인. 검증용으로 남겨뒀던 이전 세션 계정(`logtest2`, memberId=711)도 함께 정리.
- `bootRun` 프로세스 종료, MySQL/Redis 컨테이너는 계속 실행 상태로 둠(다른 로컬 개발에 재사용).
