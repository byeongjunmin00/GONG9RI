# 프론트엔드 공통 레이아웃 & 디자인 시스템

대상: frontend/design-system     <!-- 완료 시 docs/dev/frontend/design-system/changes/ 로 이동 -->
담당: 전용운

## 배경 / 요구

- GONG9RI는 지금까지 REST API(백엔드)만 존재하고 프론트엔드가 전혀 없다.
- 사용자 요청: "인스타 재질 인플루언서들이 환장하게끔 갬성있는 프론트"를 만들어달라 — 인스타그램/SNS 인플루언서 감성의 비주얼 톤앤매너를 가진 프론트엔드가 필요하다.
- 확정된 전제(사용자와 이미 합의):
  1. 기술 스택: **정적 HTML/CSS/JS + `fetch` 기반 REST API 호출**. React/Vue 등 프레임워크·빌드 도구 없음. `src/main/resources/static/` 하위에 작성해 Spring Boot 기본 정적 리소스 서빙을 그대로 사용한다(별도 웹서버/라우팅 불필요).
  2. 이번 작업 범위는 **개별 기능 페이지가 아니라 공통 레이아웃 + 디자인 시스템**이다. 메인/로그인/회원가입/상세/결제/마이페이지 등 개별 페이지(`docs/WIREFRAME.md` 2장)는 이 산출물 위에서 이후 별도 작업으로 순차 진행한다.
- 사전 확인 결과:
  - `docs/dev/ongoing/`에 현재 진행 중인 다른 작업 없음 → 충돌 없음.
  - `docs/policy/`(환불 트리거, 공구 성사 기준, 캐싱)에는 프론트엔드/디자인 관련 정책이 없음 → 해당 사항 없음.
  - `src/main/resources/static/`는 현재 비어 있음(클린 슬레이트).
  - `build.gradle`에 Thymeleaf 등 서버사이드 템플릿 엔진 의존성 없음 → 순수 정적 리소스 서빙 방식과 충돌 없음.

## 설계

### 1. 디렉토리/파일 구조 (무엇을 만드는가)

```
src/main/resources/static/
├── design-system.html      # 이번 작업 산출물을 눈으로 확인하는 쇼케이스(스타일가이드) 페이지
│                            #   — 색상 팔레트/타이포그래피/버튼/카드/폼/뱃지 등 컴포넌트 갤러리
├── css/
│   ├── tokens.css           # 디자인 토큰 정의(색상/타이포/스페이싱/라운드/그림자 등 변수)
│   ├── base.css             # 리셋 및 전역 기본 스타일
│   ├── layout.css           # 공통 레이아웃(헤더/푸터/컨테이너/그리드) 스타일
│   └── components.css       # 버튼/카드/폼/뱃지 등 재사용 컴포넌트 스타일
├── js/
│   ├── include.js           # 공통 헤더/푸터 partial을 각 페이지에 삽입하는 유틸
│   └── api.js                # REST API 호출 공통 fetch 래퍼(베이스 URL, 에러 처리 등) 뼈대
└── partials/
    ├── header.html           # 공통 헤더(로고/내비게이션/로그인·회원가입 영역)
    └── footer.html           # 공통 푸터
```

- `index.html`은 이번 작업에서 만들지 않는다 — 와이어프레임상 `/`(메인 페이지)가 차지할 자리이므로, 이후 메인 페이지 작업과의 충돌/재작업을 피하기 위해 이번 쇼케이스는 `design-system.html`이라는 별도 경로에 둔다.
- 파일 내부의 정확한 마크업 구조, CSS 값(색상 코드·폰트·수치), JS 로직 구현은 이 계획의 범위가 아니며 Generate 단계에서 정한다.
- 향후 개별 페이지(메인 등)는 위 `css/`, `js/`, `partials/`를 `<link>`/`<script>`로 그대로 재사용한다. 페이지별 디렉토리 배치는 해당 페이지 작업의 Plan에서 별도로 정한다.

### 2. 톤앤매너 방향성 (방향만, 구체 값 아님)

- 무드: 인스타그램 피드/스토리 감성 — 이미지 중심, 여백감 있는 레이아웃, 미니멀하되 생기 있는 포인트 컬러 사용.
- 컬러: 뉴트럴(화이트/오프화이트/차콜 계열) 베이스 위에, 인스타그램 브랜드를 연상시키는 웜톤 그라디언트 계열(코럴/핑크/퍼플/오렌지 방향)을 포인트로 쓰는 방향. 정확한 색상 값·팔레트 체계는 `tokens.css`에서 Generate가 정한다.
- 타이포그래피: 깔끔한 산세리프 기반 본문 + 브랜드/헤딩 요소에 포인트를 줄 수 있는 스케일 구성. 정확한 폰트·크기 체계는 Generate가 정한다.
- 레이아웃: 카드 기반 그리드를 기본으로 한다. 와이어프레임상 상품 카드(이미지+상품명+가격+공구가)가 메인/상세/마이페이지에서 반복되는 핵심 단위이므로, 카드 컴포넌트를 디자인 시스템에서 우선순위 높게 다룬다. 라운드 코너·부드러운 그림자 등 "SNS스러운" 입체감을 방향으로 삼는다.
- 반응형: 모바일 우선을 기본 방향으로 삼는다(인플루언서 SNS 유입 특성상 모바일 트래픽 비중이 클 것으로 전제). 브레이크포인트 등 구체 값은 Generate가 정한다.

### 3. 공통 컴포넌트 목록 (WIREFRAME.md 2장 기준으로 도출)

| 컴포넌트 | 용도 | 향후 쓰일 페이지(참고) |
|---|---|---|
| Header | 로고, 내비게이션(메인/로그인/회원가입/판매물품등록), 로그인 상태 표시 영역 | 전 페이지 공통 |
| Footer | 사업자 정보/링크 등 | 전 페이지 공통 |
| Button | primary/secondary 등 variant | 전 페이지 공통(로그인, 결제하기, 등록하기 등) |
| Card | 상품 카드(이미지+상품명+가격+공구가) | 메인, 상세, 마이페이지 |
| Badge/Tag | 공구 상태(모집중/성사/미성사 등) 표시 | 상세, 마이페이지(팀 상태와 연동 예상) |
| Form 요소(input/label 조합) | 로그인/회원가입/상품등록 폼 | 로그인, 회원가입, 판매물품등록 |

이번 단계에서는 위 컴포넌트의 "존재를 인지하고 스타일 시스템을 잡아두는" 것까지가 범위다. 각 페이지의 실제 마크업/데이터 바인딩은 해당 페이지의 개별 Plan에서 진행한다.

### 4. 헤더 로그인 상태 — 스코프 경계

- 현재 `docs/api/auth.md` 기준으로 "현재 로그인한 사용자 조회" 전용 엔드포인트는 없다(로그인/회원가입 성공 응답에만 사용자 정보가 담긴다).
- 이번 작업에서 헤더는 **비로그인 상태를 기준으로 한 정적 마크업**(로그인/회원가입 링크 노출)으로 구성하고, 로그인 여부에 따라 헤더 표시를 실제로 전환하는 세션 연동은 범위에서 제외한다. 이는 로그인 관련 개별 페이지 작업에서 다시 다룬다.
- (승인 시 이 경계에 이견이 있으면 지금 알려달라 — 별도 확인 필요 항목으로 남겨둔다.)

### 5. 페이지 재사용(include) 전략 방향

- 정적 HTML에는 서버사이드 include가 없다. 각 페이지 HTML이 로드된 뒤, 공용 스크립트(`include.js`)가 `partials/header.html`, `partials/footer.html`을 fetch로 가져와 페이지 내 지정된 컨테이너에 삽입하는 방식으로 헤더/푸터 중복 작성을 피한다.
- 구체적인 삽입 로직/함수 시그니처 등은 Generate 단계에서 정한다.

## 태스크

- [ ] `static/css/tokens.css` — 디자인 토큰(색상/타이포/스페이싱/라운드/그림자 등) 정의
- [ ] `static/css/base.css` — 리셋/전역 스타일
- [ ] `static/css/layout.css` — 헤더/푸터/컨테이너/그리드 레이아웃
- [ ] `static/css/components.css` — 버튼/카드/폼/뱃지 컴포넌트 스타일
- [ ] `static/partials/header.html`, `static/partials/footer.html` — 공통 헤더/푸터 마크업
- [ ] `static/js/include.js` — partial 삽입 유틸
- [ ] `static/js/api.js` — 공통 fetch 래퍼 뼈대(이후 개별 페이지가 재사용)
- [ ] `static/design-system.html` — 색상/타이포/버튼/카드/폼/뱃지 샘플을 모은 쇼케이스 페이지
- [ ] `SecurityConfig` 인가 규칙 검토 — 비로그인 사용자도 정적 프론트 리소스(`design-system.html`, `css/**`, `js/**`, `partials/**`)에 접근 가능하도록 조정 필요 여부 확인 및 필요 시 반영 (리스크 참고, 구체 matcher 패턴은 Generate가 정함)

## 평가(통과) 기준

- 이번 작업은 자바 도메인 로직 변경이 없어 `./gradlew test`류 계산적 평가는 해당 사항이 제한적이다(단, `SecurityConfig`를 건드리면 기존 인증 관련 테스트가 깨지지 않는지는 `./gradlew test`로 확인한다).
- `./gradlew bootRun`으로 앱을 구동한 뒤 브라우저에서 직접 확인한다:
  - 비로그인(세션 없음) 상태로 `http://localhost:8080/design-system.html` 접속 시 로그인 요구 없이 정상 로드되는가 (Security 리스크 해소 확인)
  - 헤더/푸터가 partial 삽입 방식으로 모든 확인 페이지에 정상 표시되는가
  - 쇼케이스 페이지에서 색상 팔레트/타이포그래피/버튼(variant별)/카드/뱃지/폼 요소가 렌더링되는가
  - 브라우저 창 폭을 좁혀도(모바일 뷰) 레이아웃이 깨지지 않는가
  - 브라우저 개발자도구 콘솔에 JS 에러(특히 partial fetch 실패)가 없는가
  - (정성적) 인스타그램/인플루언서 감성이라는 목표에 부합하는지 실제 화면을 보고 판단 — 자동화된 기준으로 대체 불가하므로 사용자 육안 확인/피드백을 거친다.

## 리스크 / 전제

- **Spring Security 인가 규칙 충돌 가능성**: 현재 `SecurityConfig`는 `/api/auth/**`, `GET /api/products/**`만 `permitAll`이고 나머지는 `anyRequest().authenticated()`다. 정적 리소스(`/`, `*.html`, `/css/**`, `/js/**`, `/partials/**`)도 동일한 필터체인을 통과하므로, 별도 허용 규칙이 없으면 비로그인 사용자가 프론트 페이지 자체를 열람하지 못하는 충돌이 생길 수 있다.
- **로그인 상태 API 부재**: 헤더에서 로그인 여부에 따라 표시를 전환하려면 현재 없는 "현재 로그인 사용자 조회" 성격의 엔드포인트가 필요할 수 있다. 이번 단계는 스코프 밖으로 규정했지만, 추후 로그인 관련 페이지 작업에서 다시 논의가 필요한 항목으로 남는다.
- **정적 파일 직접 열람(`file://`) 시 API 연동 불가 가능성**: `fetch`로 REST API를 호출하므로, 개발/확인 시 `./gradlew bootRun`으로 서버를 띄운 뒤 같은 오리진(`http://localhost:8080/...`)으로 접속해야 세션 쿠키·API 호출이 정상 동작한다. 브라우저로 HTML 파일을 직접 열면(`file://`) 정상 동작하지 않을 수 있다.
- **CORS**: 정적 리소스와 API가 같은 Spring Boot 앱·같은 오리진에서 서빙되므로 원칙적으로 별도 CORS 설정은 불필요할 것으로 전제한다.
- **기존 도메인 코드 영향 최소**: 이번 작업은 신규 정적 리소스 추가와 `SecurityConfig` 인가 규칙 조정(필요 시)에 한정되며, 기존 컨트롤러/서비스/엔티티 로직에는 영향을 주지 않는 것을 전제로 한다.
- **디자인 방향성의 주관성**: "인스타그램 감성"은 정성적 기준이라 완성 후 사용자 육안 확인/피드백이 필요하다.
