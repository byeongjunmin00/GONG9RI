# 브라우저 에러 페이지 신규 — 날 JSON·틀린 안내 제거

대상: frontend/error-page
담당: 민병준

## 배경

세션 마무리 중 "더 손볼 게 있나" 점검하다 실측으로 발견했다.

```
GET /nonexistent-path
→ 401 {"success":false,"code":"UNAUTHORIZED","message":"로그인이 필요합니다."}
```

사용자가 오타를 내고 들어오면 브라우저에 **날 JSON이 그대로** 뜨고, 게다가 **없는 주소인데 "로그인이 필요합니다"라는 틀린 안내**를 한다. 사용자가 "틀린 안내니까 고치는 게 좋겠다"고 판단해 진행.

## 변경

`Accept` 헤더로 브라우저 탐색과 프로그램 호출을 구분해, **브라우저에만** `/error.html`을 보여준다. 상태 코드와 인가 규칙은 그대로다. 상세 근거는 `design.md` 참고.

**인가 규칙(기본 차단)을 뒤집지 않은 것**이 이 작업의 핵심 판단이다 — "`/api/**`가 아니면 permitAll"로 바꾸면 확장자 없는 경로가 404가 되지만, 나중에 non-API 엔드포인트를 추가하면 자동으로 공개되는 함정이 생긴다.

## 태스크

- [x] `static/error.html` + `.error-page*` CSS
- [x] `BrowserRequests` 유틸 (Accept 기반 판정)
- [x] `ApiAuthenticationEntryPoint`(401) / `GlobalExceptionHandler`(404) 분기 연결
- [x] `ErrorPageResponseTest` 6케이스 (회귀 방지 3건 포함)
- [x] 로컬 실서버 실측 (브라우저 302→error.html / fetch JSON 유지)
- [x] 전체 407케이스 통과

## 평가(통과) 기준

- 브라우저로 없는 주소에 들어가면 에러 페이지가 보인다.
- **프론트 `fetch`는 기존 JSON(`code`/`message`)을 그대로 받는다** — 이게 깨지면 로그인 배너·결제 실패 안내 등 프론트 전체 에러 처리가 망가진다.
- 에러 페이지 자체는 비로그인으로도 열린다.

## 배운 것

**보안 설정의 기본값을 뒤집는 것과, 응답의 표현만 바꾸는 것은 전혀 다른 크기의 변경이다.** 처음엔 "확장자 없는 경로도 permitAll로 열면 404가 나오니 간단하다"고 생각했는데, 그건 `anyRequest()`의 기본 정책을 차단에서 허용으로 바꾸는 일이었다. 눈에 보이는 증상(틀린 안내)은 같아도, 표현 계층에서 고치면 되는 것을 인가 계층에서 고치면 나중에 훨씬 비싼 대가를 치를 수 있다.
