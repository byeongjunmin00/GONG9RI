# 상품 상세조회 페이지 (`/products/{id}`)

대상: frontend/product-detail
담당: 전용운

## 배경 / 요구

`docs/WIREFRAME.md` 흐름상 메인 페이지 다음 단계인 "4. 상세조회 페이지"를 만든다. 메인 페이지(`index.html`)의 상품 카드는 현재 `href="#"` placeholder(`TODO(상세 페이지 작업 시 갱신)` 주석)로만 존재하므로, 이번 작업으로 실제 상세 페이지가 생기면 그 링크를 실제 경로로 갱신한다.

상세 페이지는 상품 기본 정보 + 공동구매 팀 목록을 보여주고, 세 가지 사용자 액션(혼자 구매하기 / 기존 팀 참가하기 / 신규 팀 신설하기)의 진입점이 된다. 이 중 "혼자 구매하기"와 "신규 팀 신설 후 결제"는 결제창(`/checkout`, `docs/WIREFRAME.md` 5번 페이지)으로 이어지는데, 결제 페이지는 아직 프론트에 존재하지 않는다(`POST /api/payments` 백엔드 API 자체는 `docs/api/payment.md`에 있음). 이번 작업의 스코프 경계와 처리 방향은 "설계" 절에 명시한다.

## 설계

### 산출물 / 라우팅

- 신규 정적 페이지: `src/main/resources/static/product.html` + 전용 스크립트 `src/main/resources/static/js/product.js`.
- 라우팅 방식: **쿼리스트링**으로 상품 ID를 전달한다 — 예: `product.html?id=1`.
  - 이유: 정적 리소스 서빙 방식(Spring Boot 기본 static resource handler)에서는 `/products/{id}` 같은 경로 세그먼트를 특정 정적 파일에 매핑할 서버 라우팅이 없다(그런 매핑을 만들려면 별도 forward 컨트롤러가 필요하며 이는 이번 프론트 작업 범위를 넘는 백엔드 변경이다). `login.html`/`signup.html`/`index.html`과 같은 파일 기반 규칙을 유지하면서 동적 파라미터만 쿼리스트링으로 받는 편이 현재 구조와 일관된다.
  - `docs/WIREFRAME.md`의 `/products/{id}` 표기는 논리적 경로 설명으로 간주하고, 실제 구현 경로는 `product.html?id={productId}`로 확정한다.
- 신규 CSS 규칙이 필요하면 기존 `css/components.css`에 추가한다(토큰/베이스/레이아웃/헤더·푸터 partial은 기존 그대로 재사용). 정확히 어떤 클래스를 추가할지는 Generate 단계에서 정한다.

### 데이터 흐름

1. `product.js`가 로드 시 현재 URL의 `id` 쿼리 파라미터를 읽는다.
   - 파라미터가 없거나 숫자로 해석 불가능한 값이면, API 호출 없이 "잘못된 접근" 상태를 안내한다(main-page의 로딩/빈 목록/에러 상태 안내 패턴 재사용).
2. `GET /api/products/{id}`로 상품 상세(이름/설명/기본가/최대인원/`priceTiers`)를 가져와 렌더링한다.
   - `PRODUCT_NOT_FOUND`(404) 시 "상품을 찾을 수 없습니다" 류의 안내 상태로 전환한다(크래시 없이).
3. `GET /api/products/{id}/teams`로 모집중(`RECRUITING`) 팀 목록을 가져와 렌더링한다.
   - 이 API는 `RECRUITING` 상태만 반환하므로(API 명세), 이 페이지에서 `SUCCESS`/`FAILED` 뱃지가 실제로 나타날 일은 없다. 다만 뱃지 매핑은 응답의 `status` 값 기반으로 일반화해 구현하고, `SUCCESS`/`FAILED` 값이 오더라도 기존 디자인 시스템의 `.badge-recruiting`/`.badge-success`/`.badge-failed`에 대응시킨다.
   - 목록이 빈 배열이면 "아직 모집 중인 공구팀이 없습니다" 류의 빈 상태(에러 아님)로 안내한다.
4. 두 호출을 순차/병렬로 처리할지는 Generate 단계에서 정한다(Plan은 "둘 다 호출해 함께 렌더링한다"까지만 규정).

### 화면 구성 (컴포넌트 재사용 방향)

- 상품 정보 영역: 기존 카드/타이포 컴포넌트를 재사용해 상품명, 설명, 기본가, 가격구간표(`priceTiers` — 몇 명 이상 모이면 얼마)를 표시한다.
- 팀 목록 영역: 각 팀을 항목으로 나열하고 현재 인원/최대 인원, 상태 뱃지(`badge-recruiting` 등, 위 매핑 규칙)를 표시한다. 각 팀 항목에 "참가하기" 버튼을 둔다.
- 액션 버튼 영역:
  - "혼자 구매하기" 버튼
  - "계속 쇼핑하기" 버튼 — 메인 페이지(`/`)로 이동
  - "신규 팀 신설하기" 버튼
- 공통 안내/에러 배너: auth 페이지의 `.form-alert`/`.form-alert--error`/`.form-alert--success` 패턴을 재사용해 액션 결과(성공/실패)를 알린다.
- 사용자 입력이 아닌 서버 응답 문자열(상품명/설명/판매자명/에러 message 등)도 auth·main-page 선례와 동일하게 `textContent`로만 대입해 XSS를 방지한다(`innerHTML` 미사용).

### 액션 처리 방향

- **혼자 구매하기**: 결제 페이지(`/checkout`)가 없으므로, 클릭 시 실제 이동/결제 API 호출 없이 "결제 기능은 준비 중입니다" 류의 안내 배너만 노출한다(메인 페이지가 상세 링크를 `href="#"` placeholder로 둔 것과 동일한 패턴). `POST /api/payments` 호출은 이번 작업 범위 밖.
- **계속 쇼핑하기**: 메인 페이지(`/`)로 이동하는 링크/버튼.
- **기존 팀 참가하기**(팀 항목별 버튼): `POST /api/teams/{teamId}/join` 호출.
- **신규 팀 신설하기**: `POST /api/products/{id}/teams` 호출.
  - 성공 시: `docs/api/team.md`에 "팀 신설 직후 결제 생성으로 이어진다"는 설명이 있으나, 결제 페이지가 없어 이 흐름을 이어가지 않는다. 대신 신설 성공 안내 배너를 띄우고 팀 목록을 재조회해 새로 만든 팀이 목록에 반영되게 한다. 결제 미완료 상태로 팀이 남는 것에 대한 후속 처리(리더 결제 마감/취소 정책 등)는 이번 작업 범위 밖이며, 아래 리스크에 기록한다.
- **참가/신설 공통 에러 처리**:
  - `401 UNAUTHORIZED`(미인증): "로그인이 필요합니다" 류의 안내 배너 + 로그인 페이지(`login.html`)로 가는 링크를 보여준다.
  - `403 FORBIDDEN`(판매자 계정으로 시도): 서버가 내려주는 `message`를 안내 배너에 그대로 표시한다(auth 페이지의 기존 처리 선례와 동일).
  - `409 TEAM_FULL` / `409 ALREADY_JOINED`(참가 시): 서버 `message`를 안내 배너에 표시하고, 팀 목록을 재조회해 최신 인원/상태를 반영한다.
  - `404 PRODUCT_NOT_FOUND` / `404 TEAM_NOT_FOUND`: 서버 `message`를 안내 배너에 표시하고 목록을 재조회한다.
  - 참가로 인해 정원이 채워져 팀 `status`가 `SUCCESS`로 전환되는 경우(`docs/policy/team-success-criteria.md` 참고, 실시간 전환)는 재조회한 목록/뱃지에 반영되도록만 하면 되고, 별도 축하 문구 등 세부 문구는 Generate 단계에서 정한다.

### 메인 페이지 연동

- `src/main/resources/static/index.html`(구조상 실제로는 `js/main.js`)의 카드 `href="#"` placeholder를 `product.html?id={productId}`로 교체하고, 관련 `TODO` 주석을 제거한다.

## 평가(통과) 기준

`./gradlew bootRun` 후 브라우저로 아래를 확인한다.

- 존재하는 상품 ID로 `product.html?id={id}` 접속 시 상품명/설명/기본가/가격구간표가 정상 렌더링된다.
- 존재하지 않는 상품 ID로 접속 시 크래시 없이 "상품을 찾을 수 없습니다" 류의 안내가 뜬다.
- `id` 파라미터가 없거나 숫자가 아닌 값으로 접속 시 크래시 없이 잘못된 접근 안내가 뜬다.
- 모집중 팀이 있는 상품: 팀 목록과 뱃지(모집중)가 정상 렌더링된다.
- 모집중 팀이 없는 상품: 빈 상태 안내(에러 아님)가 뜬다.
- 비로그인 상태에서 "기존 팀 참가하기"/"신규 팀 신설하기" 클릭 시 401 처리(로그인 필요 안내 + 로그인 페이지 링크)가 뜨고 페이지가 깨지지 않는다.
- 구매자 계정으로 로그인한 상태에서 신규 팀 신설 성공 시 안내 배너가 뜨고 팀 목록이 갱신된다.
- 같은 팀에 중복 참가 시 `ALREADY_JOINED` 안내가 뜬다(수동 재현 가능하면 확인, DB 상태에 따라 스킵 가능).
- 판매자 계정으로 로그인한 상태에서 참가/신설 시도 시 `FORBIDDEN` 안내가 뜬다.
- "혼자 구매하기" 클릭 시 결제 페이지로 이동하지 않고 준비 중 안내만 뜬다.
- 메인 페이지(`/`)에서 상품 카드를 클릭하면 해당 상품의 `product.html?id=...`로 정상 이동한다.
- (코드 리뷰) 상품명/설명/판매자명/서버 에러 message 등 신뢰할 수 없는 문자열이 `textContent`로만 DOM에 대입되어 있다(`innerHTML` 미사용).

## 리스크 / 전제

- `GET /api/products/{productId}/teams`는 `SecurityConfig`의 `.requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()` 패턴(Ant 스타일 `**`)에 매칭되어 비로그인 상태에서도 호출 가능한 것으로 코드상 확인했다(실제 런타임 동작은 `bootRun` 실측으로 재확인 필요). 이 경로 때문에 `SecurityConfig`를 변경할 필요는 없을 것으로 판단한다.
- 결제 페이지(`/checkout`)가 없어 "혼자 구매하기"와 "신규 팀 신설 후 결제"는 실제 결제로 이어지지 않는다(placeholder 처리). 팀 신설은 되지만 결제가 완료되지 않는 상태로 남는 것에 대한 백엔드/정책 차원의 후속 처리(예: 결제 미완료 팀/리더 처리)는 이번 작업 범위 밖이다.
- `login.js`는 로그인 성공 시 항상 `/`로 리다이렉트하며 복귀 경로 파라미터를 지원하지 않는다(`docs/dev/frontend/auth/design.md` 기존 구현). 그래서 이 페이지에서 401을 만나 로그인 페이지로 이동해도, 로그인 후 자동으로 이 상세 페이지로 돌아오지 않는다 — 기존 auth 구현의 알려진 제약이며 이번 작업에서 해결하지 않는다.
- 헤더 로그인 상태는 여전히 미연동(design-system 단계부터의 제약)이라, 로그인 여부를 사전에 알 방법이 없다. 참가/신설 버튼은 항상 노출되고 결과는 서버 응답(401 등)으로만 판정한다.
- `POST /api/teams/{teamId}/join`의 `current_count` 갱신은 동시 접근 시 정합성 보장이 필요한 지점이나(`docs/api/team.md`에 이미 명시), 이는 백엔드가 이미 처리한 부분이라 이 프론트 작업은 결과 코드(`TEAM_FULL` 등) 처리만 담당한다.
- 정적 사이트 구조상 `/products/{id}` 경로 기반 라우팅은 지원하지 않아 쿼리스트링(`product.html?id=`) 방식을 택했다 — 이후 서버사이드 라우팅이나 SPA로 전환하면 재검토가 필요하다.
