# 상품 이미지 다중 업로드 (product/image) — Plan

담당: 민병준
대상 개념/기능: `product/image` (기존 기능 확장)

## 배경 / 요구

사용자 리포트 3건이 하나로 이어진다.

> "우리는 왜 사진이 한 장밖에 안 들어가?"
> "사진 아래가 텅텅 빈 게 좀 별로인 것 같아 … 슬라이드로 더 누를 수 있게도 가능하거나"
> "사진 올리는 것도 왜 URL로만 해야 하는 거야? 휴대폰으로 들어가면 사진 넣기도 너무 힘들고"

현재 상태:
- `Product.imageUrl` — **문자열 컬럼 하나**라 구조적으로 1장뿐.
- 파일 업로드 없음. `design.md`에 "실제 파일 업로드는 지원하지 않는다"고 명시돼 있다. **이유는 저장 위치가 없어서**였다 — 컨테이너 파일시스템은 재배포 시 초기화되므로 업로드 파일이 사라진다.

## 저장 위치 문제가 해결됐다 — Railway 볼륨

**제3자 저장소(S3/Cloudinary) 없이 가능하다.** 이 프로젝트는 이미 Railway 볼륨을 쓰고 있다.

```
redis-volume  → Redis    50MB / 500MB
mysql-volume  → MySQL   243MB / 500MB
```

볼륨은 재배포와 무관하게 유지되는 저장 공간이다. GONG9RI 서비스에 볼륨을 하나 붙이면 업로드 파일이 살아남는다. **추가 계정·키·비용이 없고**, 이미 팀이 이해하고 있는 인프라라는 점이 외부 서비스보다 낫다.

### 트레이드오프 (정직하게 기록)

| 항목 | 내용 |
|---|---|
| 용량 | 볼륨은 유한하다(현재 다른 볼륨 기준 500MB). 실서비스 규모로는 부족하고, 데모/과제 규모엔 충분 |
| CDN 없음 | 이미지 요청이 전부 앱 서버를 거친다. 트래픽이 크면 부담이지만 현재 규모에선 문제없음 |
| 확장성 | 다중 인스턴스로 늘리면 인스턴스마다 다른 볼륨을 보게 되어 이 방식이 깨진다(현재는 단일 인스턴스) |

## 무엇을 (범위)

### 1) 이미지 여러 장

`product_image` 테이블 신규 — 상품 1 : 이미지 N. 표시 순서를 갖는다(대표 이미지 = 첫 번째).

**기존 데이터 호환이 설계의 제약이다.** 현재 상품 36개 중 35개가 외부 URL(pexels 등)을 쓰고 있다. 따라서 이미지 한 건은 **업로드 파일과 외부 URL 둘 다** 표현할 수 있어야 한다. 기존 `Product.imageUrl` 값은 새 구조의 첫 번째 이미지로 이어진다.

### 2) 파일 업로드

판매자가 상품 등록·수정 화면에서 **파일을 직접 선택**해 올린다(휴대폰에서 URL을 구해 붙여넣는 현재 방식이 사실상 불가능하다는 게 이 작업의 출발점). 외부 URL 입력도 그대로 남긴다 — 둘 중 편한 쪽을 쓰면 된다.

### 3) 상세 페이지 슬라이더

여러 장을 좌우로 넘겨 볼 수 있게 한다. 이미지가 1장이면 지금과 동일하게 보인다. 부수적으로 **썸네일 아래 빈 공간 문제도 이걸로 해소**된다(사용자 리포트 2번).

### 스코프 밖

- 이미지 편집(자르기·회전), 드래그로 순서 바꾸기
- CDN·외부 오브젝트 스토리지 연동
- 기존 외부 URL을 볼륨으로 옮기는 마이그레이션 — 외부 URL은 그대로 두고 표시만 통합한다

## 어떻게 (접근/설계 방향)

- **업로드 파일과 외부 URL을 한 목록에서 동등하게 다룬다.** 화면·API는 "이미지 목록"만 알면 되고, 그 항목이 업로드된 것인지 외부 링크인지는 저장 계층의 관심사다.
- **파일은 볼륨에, 경로는 DB에.** 파일 자체를 DB에 넣지 않는다(용량·백업·성능).
- **업로드 용량은 서버에서 줄여서 저장한다.** 아래 "용량 계산" 참고 — 원본을 그대로 두면 볼륨이 금방 찬다.
- **업로드는 신뢰할 수 없는 입력이다.** 파일 업로드는 전형적인 공격 표면이라, 다음을 반드시 만족해야 한다(구체 구현은 Generate에서 결정):
  - 클라이언트가 보낸 파일명을 저장 경로에 쓰지 않는다(경로 탈출 방지)
  - 확장자·Content-Type 선언을 믿지 않고 **실제로 이미지로 해석되는지**로 판정한다
  - 크기 상한을 서버가 강제한다(프론트 검증은 우회 가능)
  - 그 상품의 판매자 본인만 업로드·삭제할 수 있다
- **서빙 시 실행 가능성을 차단한다** — 업로드 디렉터리의 파일은 이미지로만 응답하고, 정적 리소스 핸들러가 임의 경로를 노출하지 않게 한다.

### 용량 계산 — 처음 제안한 5MB는 과했다

사용자에게 "한 장 5MB / 상품당 5장"을 제안했으나 볼륨 용량을 계산해보니 맞지 않는다.

```
5MB × 5장 × 20개 상품 = 500MB   ← 볼륨 하나가 상품 20개에서 참
```

**원본을 그대로 저장하지 않고 서버에서 축소·재인코딩**해야 한다. 긴 변 기준 상한을 두고 JPEG로 재인코딩하면 한 장이 보통 수백 KB로 줄어, 같은 볼륨에 훨씬 많이 담긴다. 업로드 자체는 휴대폰 사진(3~5MB)을 받아들이되 **저장은 줄여서** 한다.

| 항목 | 값 | 근거 |
|---|---|---|
| 업로드 허용 크기 | 한 장 5MB | 휴대폰 원본 사진을 거절하지 않기 위해 |
| 상품당 장수 | 5장 | 슬라이더로 넘겨 보기에 적당하고 용량도 통제됨 |
| 저장 형태 | 축소·재인코딩 | 볼륨 용량이 실제 제약이므로 필수 |

> 축소 후 실제 크기는 구현 후 측정해서 기록한다(추정값을 근거로 쓰지 않는다).

## 영향 범위 (계층/파일)

| 계층 | 대상 |
|---|---|
| 인프라 | Railway 볼륨 생성·마운트, 업로드 경로 설정 |
| DB | `product_image` 테이블 신규, 기존 `product.image_url` 데이터 이관 |
| entity/repository | `ProductImage` 신규, `Product`와의 관계 |
| dto | 상품 등록/수정 요청·응답의 이미지 표현 변경 |
| service | 업로드 저장·검증·삭제, 상품 저장 시 이미지 목록 반영 |
| controller | 업로드 엔드포인트, 업로드 파일 서빙 경로 |
| config | multipart 크기 설정(현재 미설정 → 스프링 기본 1MB라 반드시 조정), `SecurityConfig` 경로 허용 |
| 프론트 | 판매자 등록·수정 화면(파일 선택·미리보기·삭제), 상세 페이지 슬라이더, 목록 카드(대표 이미지) |
| 문서 | `docs/dev/product/image/design.md`, `docs/db/product_image.md`, `docs/api/product.md` |

## 통과(평가) 기준

- `./gradlew test` 전체 통과.
- **기존 상품 35개가 그대로 보인다** — 외부 URL 기반 데이터가 깨지지 않는 게 최우선 조건.
- 판매자가 파일로 여러 장 올리고, 상세 페이지에서 넘겨 볼 수 있다.
- **보안**: 남의 상품에 업로드 시도 거절, 이미지가 아닌 파일 거절(확장자만 바꾼 것 포함), 크기 초과 거절, 경로 탈출 시도 거절 — 각각 테스트로 고정한다.
- 재배포 후에도 업로드한 이미지가 남아있다(볼륨이 실제로 동작하는지 프로덕션에서 확인).
- 축소 후 실제 저장 크기를 측정해 기록한다.

## 리스크 / 전제

- **볼륨 마운트는 배포 설정 변경**이라, 잘못하면 앱이 기동하지 못할 수 있다. 헬스체크 게이팅이 있어 실패해도 기존 버전이 계속 서비스되지만, 배포 확인을 평소보다 신중히 해야 한다.
- **스프링 기본 multipart 상한이 1MB**다(현재 미설정). 이걸 안 올리면 휴대폰 사진 업로드가 전부 실패한다.
- **아이폰 HEIC** — 브라우저 업로드 시 대개 JPEG로 변환되지만, 원본 HEIC가 그대로 올라오면 서버에서 해석하지 못할 수 있다. 그 경우 "지원하지 않는 형식"으로 명확히 거절해야 한다(조용히 실패하면 안 된다).
- **다중 인스턴스 확장 시 이 방식은 깨진다**(인스턴스마다 다른 볼륨). 현재 단일 인스턴스 전제이며, 확장이 필요해지면 오브젝트 스토리지로 옮겨야 한다 — 알려진 한계로 기록.
- 로컬 개발에서는 볼륨이 없으므로 업로드 경로를 로컬 디렉터리로 잡을 수 있어야 한다(환경별 설정 분리).
- `docs/dev/ongoing/` 확인 결과 팀원이 같은 영역을 작업 중이지 않다.

## 승인 요청

이 계획대로 진행할지 확인 부탁. 특히 **업로드 5MB / 상품당 5장 / 저장 시 축소**가 적절한지 봐줬으면 한다.
