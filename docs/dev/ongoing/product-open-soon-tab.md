대상: product/list-enhancements

담당: 전용운

## 배경 / 요구

- 사용자 요청: 메인 페이지 카테고리 바(현재 `[전체][식품][생활/주방][뷰티][패션/잡화][디지털/가전][기타]`, `js/main.js`의 `CATEGORIES` 배열)에 **"오픈예정"을 [전체] 바로 다음(2번째) 탭으로 추가**한다.
  → 최종 탭 순서: `[전체][오픈예정][식품][생활/주방][뷰티][패션/잡화][디지털/가전][기타]`
- 탭 UX는 지금 있는 카테고리 탭들과 **완전히 동일**하게 동작한다 — 한 번에 하나의 탭만 활성화되는 배타적 단일 선택. "오픈예정"을 누르면 다른 카테고리 선택이 풀리고, 다른 카테고리를 누르면 "오픈예정" 선택이 풀린다.
- **탭별 오픈예정 상품 노출 규칙 (요구사항 확정, 기존 계획 대비 변경)**: 오픈예정 상품(`openAt`이 미래 시각)은 오픈 시각이 지나기 전까지 **자신의 실제 카테고리 탭에는 노출되지 않는다**. 이 상품은 오픈 전까지 [전체] 탭과 [오픈예정] 탭에서만 보이고, 예를 들어 실제 카테고리가 `FOOD`라도 [식품] 탭에서는 보이지 않는다. 오픈 시각이 지나면 더 이상 "오픈예정"이 아니게 되므로 자연스럽게 [식품] 탭에도 나타난다.
  - [전체]: 오픈예정 포함 전부 노출 (변경 없음)
  - [오픈예정]: 오픈예정 상품만 노출
  - [식품]/[생활·주방]/[뷰티]/[패션·잡화]/[디지털·가전]/[기타]: 그 카테고리에 속하더라도 아직 오픈 전인 상품은 제외
- **검색(keyword)은 이번 스코프 밖**이다. `category` 없이 검색어만 있는 경우(헤더 통합검색, 카테고리 미지정 메인 검색)는 오픈예정 여부와 무관하게 기존과 동일하게 동작한다(오픈예정 상품도 검색됨) — 변경하지 않는다. `category`와 `keyword`를 함께 지정하는 조합(카테고리 탭 안에서 검색)은 `category`가 지정된 것이므로 위 카테고리 제외 규칙이 그대로 적용된다(keyword 자체에 대한 새로운 규칙이 아니라 category 규칙의 자연스러운 연장).
- 기존 상태: `docs/dev/product/product-launch/design.md`는 "오픈예정"을 상품 단위 필드(`openAt`)로만 다루고, **별도 브라우징 탭/필터는 만들지 않는다**고 명시적으로 스코프 아웃했었다(5번째 줄) — "검색/카테고리/정렬은 오픈예정 여부와 무관하게 동일하게 동작한다"(22번째 줄)도 마찬가지. 이번 작업은 그 스코프 결정을 뒤집는 확장이며, **22번째 줄 서술은 이제 절반만 맞다** — "전체" 조회와 카테고리 미지정 검색은 여전히 오픈예정 여부와 무관하게 동일하게 동작하지만, **특정 카테고리를 지정한 조회는 이제 오픈예정 여부에 따라 결과가 달라진다**(위 규칙). 완료 시 이 문구를 정확하게 다시 쓴다.
- "오픈예정"은 `ProductCategory` enum(`FOOD`/`LIVING`/`BEAUTY`/`FASHION`/`DIGITAL`/`ETC`)의 실제 값이 아니다 — 상품의 진짜 카테고리가 아니라 `openAt` 기준 시간 필터다. 화면(카테고리 바 UI)에서는 다른 카테고리 pill들과 동일한 탭으로 보이지만, DB/엔티티 레벨에서 `ProductCategory`에 새 값을 끼워넣지 않는다.

## 영향 범위 (계층)

- Controller: `ProductController.list()` — 새 쿼리파라미터(`openSoon`) 수신.
- Service: `ProductService.list()` — 캐시 키 재검토(아래 "캐시 키" 절 참고), 리포지토리 호출에 전달.
- Repository: `ProductRepositoryCustom`/`ProductRepositoryImpl.findAllWithSeller()` — QueryDSL 조건 추가. `category`가 지정되고 `openSoon`이 아닐 때 "아직 오픈 전" 상품을 제외하는 조건이 **`category` 조건에 종속적으로** 붙어야 한다(카테고리 유무에 따라 켜지는 조건).
- Frontend: `static/js/main.js`(카테고리 바 렌더링 순서·`state`·URL 동기화·목록 조회), `static/js/header-search.js` + `static/partials/header.html`(카테고리 바로가기 목록 순서 동기화).
- 문서: `docs/api/product.md`(이번 계획에서 반영 완료), `docs/dev/product/list-enhancements/design.md`(SSOT 갱신), `docs/dev/product/product-launch/design.md`(스코프 서술 갱신, 22번째 줄 "절반만 맞음" 반영).
- 테스트: `ProductCachingTest`, `ProductControllerTest` 등 `findAllWithSeller`/`ProductService.list()`를 직접 호출하는 기존 테스트(시그니처가 늘어나면 호출부 전부 갱신 필요) + 카테고리 탭에서 오픈예정 상품이 제외되는지 검증하는 신규 테스트 케이스.

## 설계 (접근 방향)

### 1. UI — 카테고리 바 순서 및 배타적 단일 선택

- `js/main.js`의 `CATEGORIES` 순서를 `전체 → 오픈예정 → 식품 → 생활/주방 → 뷰티 → 패션/잡화 → 디지털/가전 → 기타`로 둔다. 렌더링·클릭 동작은 기존 카테고리 탭과 동일한 단일 선택 목록 로직을 그대로 재사용한다(오픈예정 클릭 시 `category` 해제 + `?openSoon=true` 반영, 카테고리 클릭 시 `openSoon` 해제 + `?category=` 반영). 새로고침해도 유지되도록 지금과 동일하게 URL 쿼리파라미터를 진실의 원천으로 쓴다.
- `js/header-search.js`의 정적 카테고리 바로가기 목록도 같은 순서(전체 바로 다음에 오픈예정)로 동기화한다.
- 정렬(`sort-select`)은 오픈예정 탭에서도 그대로 노출·동작한다. 오픈예정 상품은 구조적으로 아직 `RECRUITING` 팀을 가질 수 없어(product-launch 규칙) `POPULAR`/`DEADLINE` 정렬 기준이 전부 동률(NULL)로 처리되는 특성은 기존 계획과 동일하다.
- 오픈예정 상품이 하나도 없을 수 있는 상태(운영 초반)이므로, 오픈예정 탭 전용 빈 목록 문구가 필요하다(정확한 문구는 Generate가 정한다). 개별 카테고리 탭에서 "오픈예정 제외로 인해 결과가 줄어드는 것" 자체는 별도 안내 문구 없이 그냥 자연스러운 목록 결과로 취급한다(사용자가 요청한 건 노출 규칙이지 별도 안내 UI가 아님).

### 2. 백엔드 — 카테고리 탭에서 오픈예정 상품 제외

- `GET /api/products`의 동작을 다음 세 가지 경우로 나눈다(새 API 파라미터를 추가하는 게 아니라, 기존 `category`/`openSoon` 조합에 따른 **쿼리 조건 재설계**다):
  1. `category`가 없고 `openSoon`도 아닌 경우(전체 탭, 카테고리 미지정 검색 포함) → 기존과 동일, 오픈예정 여부와 무관하게 전부 노출.
  2. `category`가 지정되고 `openSoon`이 아닌 경우(특정 카테고리 탭, 이 카테고리 안에서의 검색 포함) → 해당 카테고리 조건 **AND** "오픈예정이 아님"(= `openAt`이 없거나 이미 지났음, `Product.isNotYetOpen() == false`와 동등한 조건).
  3. `openSoon=true`인 경우 → 오픈예정 상품만(기존 계획과 동일).
- `openSoon`은 여전히 `category`와 별개의 쿼리파라미터로 둔다(엔진에 새 필드를 추가하는 게 아니라 위 3가지 분기를 결정하는 입력일 뿐).

### 3. 캐시 키 — 재검토 결과: 새 축을 추가할 필요는 없다

- 원래 계획은 "`openSoon` 여부를 캐시 키에 포함해야 한다"였고, 이건 여전히 유효하다(오픈예정 탭 자체가 별도 결과 집합이라 키에 없으면 캐시가 섞인다).
- 반면 "카테고리 탭에서 오픈예정 상품을 제외하는 것"은 **새로운 축이 아니다** — `category` 값 자체(예: `FOOD`)는 그대로 캐시 키 컴포넌트로 남고, 그 값에 대응하는 쿼리의 "의미"(오픈예정 제외 여부)만 위 설계대로 항상 카테고리 유무에 종속적으로 결정된다. 즉 같은 `(page, size, category, sort, openSoon)` 조합은 항상 같은 SQL 조건으로 귀결되므로, 캐시 키를 구성하는 값 자체(파라미터 목록)는 지금 계획(`openSoon` 추가)에서 더 늘어날 필요가 없다.
- 다만 결과적으로 주의할 점: **시간이 지나 상품의 오픈예정 상태가 바뀌어도(오픈 시각 도달) 캐시는 그 자체로는 갱신 트리거가 없다** — 등록/수정/삭제 시에만 무효화되기 때문에, 특정 카테고리 탭 캐시가 TTL(30분) 동안 "방금 오픈된 상품"을 계속 누락할 수 있다. 이건 새 캐시 키 설계 문제가 아니라 기존 TTL 정책이 이미 감수하고 있는 시간 기반 낡음(staleness)과 같은 성격이라 별도 해결책을 만들지 않는다(아래 "리스크" 참고).

### 4. 헤더 검색 오버레이 "카테고리 바로가기" 동기화

- `js/header-search.js`의 정적 `CATEGORIES` 목록에도 "오픈예정" 항목을 [전체] 자리 바로 다음(참고: 이 목록엔 원래 "전체" 항목 자체가 없다 — `goToCategory(value)`가 항상 특정 카테고리 값을 요구하는 구조라, "오픈예정" 항목은 이 목록의 **맨 앞**에 추가한다) 추가해 두 목록이 계속 동기화되게 한다. 클릭 시 `index.html?openSoon=true`로 이동해야 한다(구체 구현은 Generate가 정한다).

### 5. 문서 갱신 (완료 시)

- `docs/dev/product/list-enhancements/design.md`에 "오픈예정 필터" 절 추가 — 탭 노출 규칙(전체/오픈예정/카테고리별 제외)까지 명시.
- `docs/dev/product/product-launch/design.md` 갱신:
  - 5번째 줄("별도 브라우징 탭/필터는 만들지 않는다") → `product/list-enhancements`의 오픈예정 탭을 참조하도록 고친다.
  - 22번째 줄("검색/카테고리/정렬은 오픈예정 여부와 무관하게 동일하게 동작한다") → "전체 조회·카테고리 미지정 검색은 여전히 무관하게 동작하지만, 특정 카테고리 탭 조회는 이제 오픈예정 상품을 제외한다"로 정정.

## 리스크 / 전제

- **캐시-시간 정합성**: 목록 캐시 TTL(30분, `docs/policy/caching.md`) 동안 특정 카테고리 탭 캐시가 "방금 오픈 시각이 지난" 상품을 계속 누락하거나(카테고리 탭 관점), 오픈예정 탭 캐시가 "이미 지난" 상품을 계속 포함할 수 있다(오픈예정 탭 관점). 둘 다 등록/수정/삭제로 트리거되는 무효화가 아니라 순수 시간 경과로 발생하는 낡음이라, 기존 정렬(POPULAR/DEADLINE) 결과가 TTL만큼 낡을 수 있다는 정책과 같은 성격이다. 실제 구매 차단은 항상 서버가 최종 판정하므로(product-launch 규칙) 기능 안전성엔 문제가 없다 — 목록 노출의 신선도 문제일 뿐이다.
- **기존 호출부 영향**: `findAllWithSeller`/`ProductService.list()`에 새 파라미터가 생기면 `ProductController`, `ProductCachingTest` 등 이 메서드를 직접 호출하는 모든 곳(테스트 포함)을 함께 갱신해야 한다(누락 시 컴파일 실패).
- **검색(keyword)은 스코프 밖**: `category` 없이 검색어만 있는 조회는 오픈예정 여부와 무관하게 기존과 동일하게 유지한다(오픈예정 상품도 검색 결과에 포함). `category`+`keyword` 조합은 `category` 규칙(제외)이 자연스럽게 적용되지만, 이건 keyword 자체에 대한 새 규칙을 만든 게 아니라 category 규칙의 부수 효과다. keyword만 있고 카테고리별 오픈예정 노출과 다른 별도 규칙이 필요해지면 별도 요청/계획으로 다룬다.
- **범위 밖으로 남기는 것**: 오픈예정 상품끼리의 별도 정렬 기준(예: 오픈일이 가장 임박한 순)은 이번 스코프에 없다.

## 평가(통과) 기준

- `./gradlew test` 전체 통과 (기존 테스트 시그니처 변경분 포함).
- `GET /api/products?openSoon=true` — `openAt`이 없거나 과거인 상품은 제외되고 미래인 상품만 반환됨을 확인.
- `GET /api/products?category=FOOD` — 실제 카테고리가 `FOOD`이면서 `openAt`이 미래인 상품은 결과에서 제외되고, `openAt`이 없거나 이미 지난 `FOOD` 상품만 포함됨을 확인. 해당 상품의 `openAt`이 지나면 이후 같은 조회에 포함됨을 확인(캐시 미스 상태 기준 — 캐시가 걸려있으면 TTL/무효화 전까지는 반영되지 않을 수 있다는 것도 함께 확인).
- `GET /api/products`(category·openSoon 둘 다 생략, 전체 탭) — 오픈예정 상품 포함 기존과 동일하게 전부 반환됨을 확인(회귀 없음).
- `GET /api/products?keyword=...`(category 없음) — 오픈예정 상품도 기존과 동일하게 검색 결과에 포함됨을 확인(회귀 없음).
- 캐시 검증: `openSoon=true`와 생략 요청이 서로 다른 캐시 엔트리를 쓴다는 것을 확인(기존 `ProductCachingTest`의 스파이 검증 패턴 재사용). 캐시 키에 새 축을 추가하지 않기로 한 결정이 실제로 캐시 오염을 일으키지 않는지도 같이 확인.
- 프론트: index.html 카테고리 바 순서가 `[전체][오픈예정][식품]...`인지 확인. "오픈예정" 탭 클릭 시 `?openSoon=true`로 URL이 바뀌고 다른 카테고리 선택이 해제되며 목록이 오픈예정 상품만으로 갱신됨을 수동 확인. 카테고리 탭 클릭 시 그 카테고리의 오픈예정 상품이 목록에 안 보임을 수동 확인.
- 헤더 검색 오버레이의 카테고리 바로가기 목록 맨 앞에 "오픈예정"이 추가되고 클릭 시 동일하게 동작.
