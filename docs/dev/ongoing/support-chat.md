# 관리자 1:1 실시간 상담 (support/chat) — Plan

담당: 민병준
대상 개념/기능: `support/chat` (신규)

## 배경 / 요구

> "관리자랑 1대1 대화하는 거, 실시간 고객센터 이런 거" (사용자 요청, 2026-08-21)

지금 있는 채팅은 **AI 챗봇 하나뿐**이다(`buyer-chatbot`, OpenAI 호출). 사람이 개입할 수 있는 경로가 없어서, AI가 답하지 못하는 문의(결제 오류, 환불 분쟁 같은 개별 사정)는 갈 곳이 없다. 상품 문의(`inquiry`)가 있지만 그건 **판매자에게 비동기로 남기는 글**이고, 플랫폼 차원의 문제는 다룰 수 없다.

## 무엇을 (범위)

**구매자·판매자 ↔ 관리자**가 실시간으로 주고받는 1:1 상담.

| 포함 | 제외 (스코프 밖) |
|---|---|
| 상담방 생성·목록·대화 | 여러 관리자 간 상담 배정/이관 |
| 실시간 송수신 | 파일·이미지 전송 |
| 상담 종료(닫기) | 상담 만족도·평가 |
| 관리자 미접속 시 메시지 보관 후 열람 | 자동 응답·AI 연동(기존 챗봇과 별개로 둔다) |
| 안 읽은 메시지 표시 | 타이핑 중 표시, 읽음 확인(read receipt) |

## 핵심 난점 — 지금 WebSocket에는 인증·인가가 없다

`WebSocketConfig`에 STOMP 채널 인터셉터가 **하나도 없다**(코드 확인 완료). 기존 용도인 공구팀 정원 브로드캐스트(`/topic/products/{id}/teams`)는 **공개 정보**라 문제가 없었다.

그러나 상담 내용은 **사적인 대화**다. 같은 구조로 `/topic/support/{roomId}`를 만들면 **아무나 남의 상담방을 구독해 대화를 훔쳐볼 수 있다.** 이 작업의 실질적인 본체는 채팅 UI가 아니라 **구독 권한 검사**다.

- 필요한 것: 구독 요청 시 "그 방의 당사자(방 주인) 또는 관리자"만 통과시키는 검사.
- 세션 기반 인증을 쓰고 있으므로, WebSocket 핸드셰이크 시점의 사용자 정보를 STOMP 세션에 실어 이후 구독·발행에서 쓸 수 있어야 한다.
- 발행(메시지 전송)도 같은 검사가 필요하다 — 남의 방에 메시지를 밀어 넣을 수 있으면 안 된다.

> 구체적인 인터셉터 구성·API 선택은 Generate에서 결정한다. Plan은 "구독·발행 양쪽에 권한 검사가 필요하다"까지만 정한다.

## 데이터 모델

새 테이블 2개. 기존 `chat_session`/`chat_message`는 **AI 챗봇 전용**이라 재사용하지 않는다 — 참여자 구조(구매자 1명 vs 사용자+관리자)와 수명주기가 다르고, 섞으면 양쪽 다 지저분해진다.

| 테이블 | 담는 것 |
|---|---|
| `support_room` | 상담을 연 회원, 상태(열림/닫힘), 마지막 메시지 시각, 각 측의 안 읽은 개수 |
| `support_message` | 어느 방, 보낸 사람, 내용, 보낸 시각 |

- 한 회원이 **동시에 열어둘 수 있는 방은 1개**로 제한한다(무한 생성 방지). 닫힌 방은 이력으로 남는다.
- 회원 삭제 정책과의 관계: 상담 기록은 `product/admin`의 "활동 있는 회원 하드 삭제 금지"에 걸릴 대상이 아니라, 회원과 함께 정리되는 leaf 데이터로 본다(알림·AI 로그와 같은 취급).

## API / 인터페이스

| 경로 | 용도 |
|---|---|
| `POST /api/support/rooms` | 상담 시작(이미 열린 방이 있으면 그 방을 돌려준다) |
| `GET /api/support/rooms/me` | 내 상담방 + 메시지 |
| `GET /api/admin/support/rooms` | 관리자: 상담방 목록(안 읽은 것 우선) |
| `GET /api/admin/support/rooms/{id}` | 관리자: 특정 방 + 메시지 |
| `POST /api/admin/support/rooms/{id}/close` | 상담 종료 |
| STOMP `/topic/support/{roomId}` | 실시간 수신 |

- **메시지 전송은 REST가 아니라 STOMP 발행으로 받는다**(실시간이 목적). 다만 저장은 서버가 하고, 저장 성공 후 브로드캐스트한다 — 화면에만 뜨고 DB엔 없는 상태를 만들지 않기 위해.
- 관리자가 접속 중이 아니어도 메시지는 저장된다. 관리자가 나중에 목록에서 확인한다(= "실시간이면 좋고, 아니어도 유실 없음").

## 알림 연동

관리자에게 새 상담이 열리면 기존 알림(`notification`)을 재사용한다. 알림 종류가 이미 9종이고 발행 경로(`NotificationPublisher`)가 정리돼 있어 하나 더 추가하는 비용이 작다.

> 관리자 계정에 헤더 알림벨이 노출되는지 확인이 필요하다(예전에 "관리자는 알람벨 필요없나?"라는 질문이 있었고 당시엔 없었다).

## 영향 범위 (계층/파일)

| 계층 | 대상 |
|---|---|
| config | `WebSocketConfig` — STOMP 인증/인가 인터셉터, 엔드포인트 추가 |
| entity/repository | `SupportRoom`, `SupportMessage` 신규 |
| service | 상담방 생성·조회·메시지 저장·권한 검사 |
| controller | 사용자용·관리자용 REST + STOMP 핸들러 |
| dto | 방/메시지 응답, 전송 요청 |
| 프론트 | 사용자 상담 위젯(기존 챗봇 위젯과 자리 겹침 주의), 관리자 상담 화면 |
| 문서 | `docs/dev/support/chat/design.md`, `docs/api/support.md`, `docs/db/support_room.md`·`support_message.md` |

## 통과(평가) 기준

- `./gradlew test` 전체 통과.
- **권한 테스트가 이 작업의 핵심이다**: 남의 방 구독 거절, 남의 방에 발행 거절, 비로그인 연결 거절, 관리자만 관리자 API 접근 — 각각 테스트로 고정한다.
- 로컬 실측: 두 브라우저(사용자/관리자)로 실제 대화가 오가는 것 확인.
- 관리자 미접속 상태에서 보낸 메시지가 **유실되지 않고** 나중에 보이는 것 확인.
- 상담방 동시 생성 시도에도 한 회원당 열린 방이 1개인지 확인.

## 리스크 / 전제

- **WebSocket 연결은 메모리를 잡는다.** 이 프로젝트는 이미 브로커 스레드풀 무제한 증식으로 프로덕션 OOM을 겪었고(`docs/logs/cd/deploy/003-oom-crash.md`), 지금은 `WebSocketConfig`에서 스레드풀을 작은 고정 크기로 못박아 둔 상태다. 상담 채팅은 **연결이 오래 유지되는** 성격이라 기존 브로드캐스트보다 부담이 크다 — 배포 후 메모리 추이를 확인해야 한다.
- 인메모리 심플 브로커를 쓰므로 **다중 인스턴스로 늘리면 깨진다**(인스턴스 간 메시지 전달 없음). 현재 단일 인스턴스 전제 — 이미지 볼륨과 같은 성격의 알려진 한계.
- 관리자 계정은 현재 1개다. 여러 관리자가 같은 방을 동시에 볼 때의 처리는 스코프 밖으로 둔다.
- 기존 AI 챗봇 위젯과 **화면 자리가 겹칠 수 있다**. 두 개를 어떻게 배치할지(탭으로 합칠지, 별도 진입점으로 둘지) 결정이 필요하다.
- `docs/dev/ongoing/` 확인 결과 팀원이 같은 영역을 작업 중이지 않다.

## 승인 요청

이 계획대로 진행할지 확인 부탁. 특히 아래 두 가지를 봐줬으면 한다.

1. **AI 챗봇과의 관계** — 기존 챗봇 위젯 옆에 "상담원 연결"을 두는 방식이 맞는지, 아니면 완전히 별도 진입점으로 둘지.
2. **스코프** — 위 "제외" 목록(파일 전송, 읽음 확인, 여러 관리자 배정)을 정말 빼도 되는지.
