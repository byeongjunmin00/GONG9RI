# 포트원(PortOne) 실결제 연동 — 샌드박스

대상: payment/portone            <!-- 완료 시 이 기능의 changes/로 이동 -->
담당: 전용운

## 배경 / 요구

지금 `payment/crud`(`PaymentService.create`, `docs/dev/payment/crud/design.md`)는 실제 PG 연동이 전혀 없는 더미 기능이다 — `POST /api/payments` 호출 한 번으로 곧바로 `PAID` 레코드를 DB에 기록할 뿐, 실제 결제창이 뜨거나 카드 승인이 실제로 이루어졌는지 확인하는 절차가 없다. 환불도 마찬가지로 `team/deadline-check` 스케줄러(`docs/policy/refund-trigger.md`)가 DB의 `status`만 `REFUNDED`로 바꾸는 것이지 실제 PG 취소 API를 호출하지 않는다.

팀원이 결제대행 중개 서비스 **포트원(PortOne)**의 테스트(샌드박스) 환경으로 실제 결제 연동을 시도해보기로 함에 따라, 이 문서는 그 연동의 백엔드 설계를 다룬다. 포트원은 V2 API 기준 사업자등록증 없이도 테스트 연동이 가능하다(관리자콘솔에서 [설정 모드]를 "테스트"로 두면 네이버페이·토스·페이팔을 제외한 대부분 PG사의 테스트 credential 사용 가능) — 이번 스코프는 이 테스트 모드로 국한하고, 실제 라이브 전환(사업자등록·정산 계좌 연결 등)은 스코프 밖이다.

## 설계

### 이번에 좁힌 스코프 (기본값으로 정함 — 이견 있으면 확인 필요)

- **결제수단**: ~~카드 결제만 다룬다~~ → **정정(2026-08-12, Generate 완료 후 실측으로 발견)**: 포트원 콘솔에 실제로 연결된 테스트 채널이 카드가 아니라 **카카오페이**(PG Provider: `kakaopay`, MID: `TC0ONETIME`)로 확인됨 — 사용자 승인 하에 **카카오페이 간편결제만** 다루는 것으로 스코프 정정. `payMethod`도 `CARD`에서 `EASY_PAY`로 변경. 카드·계좌이체·가상계좌·다른 간편결제사(네이버페이 등)는 여전히 스코프 밖(이후 채널 추가로 확장 가능).
- **환불 경로**: 사용자가 자발적으로 결제를 취소하는 기능은 다루지 않는다. 지금 있는 유일한 환불 경로("공구팀 미성사 → 자동환불")가 DB 상태 전환 대신 실제 PG 취소 API를 호출하도록 바꾸는 것까지만 다룬다.
- **팀 참가-결제 결합 방식은 바꾸지 않는다**: 지금처럼 `team/join`(참가)과 `payment/create`(결제 기록)는 별개 API 호출로 유지한다. 이 둘의 순서/커플링을 재설계하는 건 `team/crud`까지 건드리는 별개의 큰 작업이라 이번 스코프에서 제외한다(아래 리스크에 사실만 남긴다).
- **프론트엔드**: 기존 `product.html`/`checkout.html`의 결제 버튼이 포트원 SDK로 결제창을 여는 최소 연동까지만 포함한다. 디자인/UX 다듬기는 스코프 밖.

### 바뀌는 흐름

- **지금**: `POST /api/payments` 호출 한 번 → 즉시 `PAID` 레코드 생성(가짜 결제, 서버측 검증 없음).
- **바뀔 것**: "결제 요청 생성(서버가 주문정보 발급) → 클라이언트가 포트원 결제창을 열어 사용자가 테스트카드로 결제 → 서버가 그 결과를 포트원 API로 재조회해서 실제 승인 여부·금액을 직접 확인한 뒤에만 확정"하는 흐름으로 바뀐다. **클라이언트가 보내는 "성공했다"는 값을 그대로 믿지 않고, 서버가 포트원 쪽에 재확인하는 절차가 반드시 있어야 한다** — 이번 설계의 핵심 원칙.
- 환불(팀 미성사 자동환불)도 "DB 상태만 REFUNDED로 전환"에서 "포트원 결제취소 API 호출 → 성공 확인 후 DB 상태 전환"으로 바뀐다.

### API/DB 계약 (Generate 이전에 확정 필요)

- `POST /api/payments`의 의미가 바뀐다 — 기존엔 "결제 완료" 응답이었지만, 이제는 "결제 요청이 접수됨(승인 대기)" 응답이어야 한다. 실제 확정은 별도 시점(포트원 웹훅 또는 결제 완료 후 프론트가 호출하는 확인 API)에 이루어진다. 정확한 API 형태는 `docs/api/payment.md` 갱신으로 확정한다.
- 신규: 포트원이 결제 결과를 우리 서버에 알려주는 **웹훅 수신 엔드포인트**가 필요하다 — 세션 인증을 요구할 수 없는 대신(PG가 호출하는 것이라), 포트원이 실제로 보낸 요청인지 검증하는 절차가 있어야 한다.
- `payment` 테이블에 **PG 거래를 식별할 컬럼**이 추가로 필요하다 — 없으면 어떤 결제를 취소해야 하는지, 웹훅이 어느 결제 건에 대한 것인지 특정할 수 없다. 정확한 컬럼명·타입은 `docs/db/payment.md` 갱신 시 확정한다.
- `PaymentStatus`(지금 `PAID`/`REFUNDED` 둘뿐)에 "승인 대기" 성격의 중간 상태가 최소 1개 더 필요해 보인다 — 정확한 값 이름은 Generate가 정한다.

## 리스크 / 전제

- **팀 참가-결제 순서 문제(재설계 안 함, 사실만 남김)**: 지금 구조에서는 결제 없이도 `team/join` 호출만으로 팀 참가가 확정된다 — 실제 PG를 붙여도 이 순서는 그대로라, "결제를 안 했는데 참가는 확정된" 상태가 이론상 여전히 가능하다. 이번 스코프에서는 이 문제를 해결하지 않고 있는 그대로 인지만 한다.
- **사업자등록증**: 테스트 연동 자체엔 불필요하다고 확인됐다(포트원 공식 문서 기준). 다만 카카오페이를 실계약으로 연결하려면 필요해질 수 있는데, 이번엔 테스트 채널만 쓰므로 해당 없음.
- **웹훅 로컬 테스트의 어려움**: 포트원 웹훅은 공인 URL로만 오므로 로컬(`localhost`) 환경에서는 직접 못 받는다 — 터널링 도구가 필요하거나 Railway 배포 환경에서만 실측 가능할 수 있다(구체 해결은 Generate).
- **멱등성**: 웹훅이 PG의 재시도 정책으로 중복 도착할 수 있다 — 같은 결제 건이 두 번 확정 처리되지 않게 하는 보장이 필요하다(해결 방식은 Generate).
- 테스트 모드라 실제 금전 이동이 없어 되돌리기 어려운 변경은 아니다. 다만 포트원 계정 가입·PG 채널 연결은 팀원의 브라우저 조작이 필요하다.
