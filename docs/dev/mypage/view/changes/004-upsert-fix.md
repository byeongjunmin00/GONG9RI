# 판매자 수익 요약(seller_revenue_summary) — 조회 시 부트스트랩 → 결제 시 upsert로 전환

## 배경 / 요구

`docs/dev/mypage/view/changes/003-precomputed-revenue.md`(Redis 캐싱 → 집계 컬럼 전환)의 뒤를 잇는 **정정 작업**이다.

Evaluate 때 "부트스트랩 vs 신규 결제 경쟁" 리스크로 남겨뒀던 문제를 사용자와 다시 짚어보니, 근본 원인은 **요약 행 생성 시점이 잘못 잡혀 있었던 것**으로 확인됨:

- 현재: 요약 행은 **판매자가 자기 수익 페이지를 조회할 때**(`SellerMypageService.revenue()`) 없으면 그제서야 만들어진다(지연 부트스트랩).
- 문제: 결제(`PaymentService.create()` → `incrementPaid`)는 "행이 있으면 증가시켜라"는 조건부 UPDATE라서, 아직 조회된 적 없는 판매자에게 결제가 들어오면 **행이 없어 조용히 무시된다**(0건 영향, 에러 없음). 그 상태에서 조회(부트스트랩)가 그 결제와 타이밍이 겹치면, 부트스트랩이 그 결제를 못 본 채로 행을 만들고, 그 결제의 증가분은 영구히 어디에도 반영되지 않는다.
- 사용자 지적대로, **요약 행은 "판매자가 조회하는 시점"이 아니라 "결제가 발생하는 시점"에 이미 있어야 한다.** 지금 구조는 두 가지 다른 문제("결제 시점의 정상적인 행 생성"과 "이번 기능 도입 이전 과거 데이터 보정")를 하나의 로직(조회 시 부트스트랩)에 뭉쳐놔서 생긴 설계 오류다. 이 둘을 분리한다.

## 설계

- **결제/환불 시점에 행이 즉시 생기도록 전환**: `SellerRevenueSummaryRepository.incrementPaid`를 "행이 없으면 그 결제 값으로 새로 만들고, 있으면 증가시켜라"(upsert)로 바꾼다. 이러면 판매자의 **첫 결제가 들어오는 순간** 요약 행이 정확한 값으로 생기고, 조회 여부와 무관해진다 — 지금 얘기하는 경쟁 상황 자체가 사라진다.
- **`SellerMypageService.revenue()`를 순수 조회로 단순화**: 조회 시 행을 만드는(쓰기) 로직을 제거한다. 행이 없으면 결제가 한 번도 없었다는 뜻이므로 그냥 0을 반환한다(위 전환 이후엔 이게 항상 맞는 해석이 됨).
- **과거 데이터 보정(백필)은 별도의 일회성 문제로 분리**: 이번 기능(집계 컬럼) 도입 *이전부터* 존재하던 결제 이력이 있는 판매자는, upsert 방식이 도입돼도 그 이전 이력이 요약 행에 반영 안 돼 있을 수 있다. 이건 "조회마다 신경 쓸 문제"가 아니라 "배포 시점에 한 번만 처리하는 문제"로 봐야 한다 — 구체 메커니즘(1회성 백필 작업 vs 다른 방식)은 Generate가 판단. 현재 로컬 DB는 결제 0건이라 당장 백필 대상은 없지만, 메커니즘 자체는 마련해야 한다.
- **환불 경로 관련 리스크**: 환불(`TeamDeadlineService.processDeadline()` → `applyRefund`)은 항상 "이미 PAID였던 결제"를 대상으로 하므로, 결제 시점에 upsert가 정상 동작했다면 환불 시점엔 요약 행이 이미 존재해야 한다. 단, **백필이 안 된 과거 이력 판매자**에게 환불이 먼저 들어오는 경우는 여전히 다뤄야 할 문제로 남는다 — 이번 스코프에서 해결을 강제하지 않고 리스크로만 명시(백필이 upsert 전환과 함께/이전에 실행돼야 한다는 전제가 생김).

## 태스크

- [ ] `SellerRevenueSummaryRepository.incrementPaid`를 upsert(생성+증가 원자적 처리)로 변경
- [ ] `applyRefund`(환불 감소 경로) 동작 재검토 — 정상 흐름 전제(행이 이미 있음)를 문서화하고, 백필 전제가 깨졌을 때의 동작을 최소한 명시적으로 남김(에러 없이 조용히 무시되는 현재 방식이 맞는지 판단)
- [ ] `SellerMypageService.revenue()`에서 조회 시 부트스트랩(쓰기) 로직 제거, 순수 조회로 단순화
- [ ] 과거 데이터 백필 메커니즘 마련(구체 방식은 Generate 판단) + 필요 전제 문서화
- [ ] 기존 "조회 시 부트스트랩" 가정을 검증하던 테스트를 새 동작에 맞게 수정/제거
- [ ] 신규 테스트: 한 번도 결제 없던 판매자에게 동시에 첫 결제 두 건 이상이 들어와도(경쟁 상황) 정확히 합산되는지 정면으로 검증
- [ ] 신규 테스트: 결제가 하나도 없는 판매자는 부트스트랩 없이도 정확히 0을 반환하는지 확인
- [ ] `docs/db/seller_revenue_summary.md`, `docs/dev/mypage/view/design.md`에서 "조회 시 부트스트랩" 서술을 새 방식으로 교체
