# 002 — 관리자 상품 삭제

## 배경

관리자 화면은 상품/환불을 **읽기 전용**으로 시작했다(001의 스코프 결정). 사용자가 "관리자니까 글도 삭제할 수 있게 해줘"라고 요청해 상품 삭제만 예외적으로 쓰기 액션을 추가한다.

## 결정

| 결정 | 근거 |
|---|---|
| 삭제 정책을 회원 삭제와 동일하게 | 이미 `MEMBER_HAS_ACTIVITY`로 "활동 기록이 있으면 하드 삭제 금지" 정책이 있다. 상품도 같은 결이어야 사용자가 규칙을 두 번 배우지 않는다 |
| 결제·공구팀·리뷰 → 거절(409) | 돈과 공개 기록이 걸려 있다. 정산·환불 근거가 깨진다 |
| 찜·문의·가격구간·이미지 → 함께 삭제 | 다른 테이블이 참조하지 않는 leaf이고, 상품이 사라지면 의미도 없다 |
| 판매자 삭제와 같은 내부 경로 사용 | 따로 구현하면 삭제 정책이나 캐시 무효화가 한쪽만 고쳐진다 |
| 목록은 기존 공개 API 재사용 | 001과 동일 — `GET /api/products`가 이미 전체를 페이지네이션 조회한다 |

## 함께 막은 기존 구멍

이 가드는 관리자 기능을 만들며 넣었지만 **판매자 삭제에도 원래 없던 것**이다. 가드 없이 결제가 달린 상품을 지우면 `payment.product_id`의 FK(`NO ACTION`)가 DELETE를 거부한다 — 로컬 DB에서 직접 재현해 확인했다(`ERROR 1451 (23000)`).

## 알아둘 것 — 이 500 경로는 테스트로 못 본다

가드를 지워도 테스트는 500이 아니라 **204**를 낸다. `@Transactional` 테스트는 롤백이라 `DELETE`가 DB까지 가지 않고, FK 위반은 커밋 시점에 터지기 때문이다. 그래서 테스트가 고정하는 건 "409로 거절한다"는 계약이고, FK가 막는다는 근거는 위 실측이다(테스트 주석에도 명시).

같은 이유로 **커밋 시점에 터지는 문제는 전부 이 테스트 방식으로 못 잡는다** — FK 위반, 지연 제약, `AFTER_COMMIT` 훅.
