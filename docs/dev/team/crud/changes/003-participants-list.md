# 공구팀 상세 — 참여자 목록 표시

대상: team/crud (기존 기능 확장, 새 폴더 아님)
담당: (미정)

## 배경 / 요구

공구팀 상세(현재 구현상 "상세 화면"은 별도 페이지가 아니라 `product.html`의 "모집 중인 공구팀" 목록에서 각 팀을
나타내는 `team-item` 한 줄이다 — `js/product.js`의 `createTeamItem()`)에서, 그 팀에 이미 참여한 사람이 누구인지
보여준다. 참가를 고민하는 구매자가 "누가 벌써 참여했는지" 보고 참여 결정에 참고하도록 돕는 목적이다.

개인정보 노출을 막기 위해 실명·프로필 사진·연락처는 노출하지 않고, 닉네임(또는 마스킹된 이름) + 참여 시각(대략적
단위) + 팀장 여부만 보여준다(사용자와 이미 합의된 방향).

이번 작업은 `docs/dev/team/crud/changes/002-target-participants.md`(공구팀 신설 시 목표 인원 선택) 위에
이어지는 `team/crud` 확장이다.

## 조사 결과 (현재 상태)

- **닉네임 필드 없음**: `Member` 엔티티(`entity/Member.java`)는 `username`(로그인 아이디)·`name`(실명, `NOT
  NULL`)만 있고 닉네임/표시이름 필드가 없다(`docs/db/member.md`도 동일). 닉네임을 입력받는 가입/프로필 UI도
  없다.
- **참여 관계**: `GroupBuyTeam`은 `leader`(신설자) 하나만 연관관계로 갖고, 전체 참여자는 별도 조인 엔티티
  `TeamParticipation`(`team_id`+`member_id`, `docs/db/team_participation.md`)에 담긴다. 팀 신설 시
  리더(`TeamService.create()`)와 참가 시 참가자(`TeamService.joinWithLock`/`joinAtomic`) 모두 이 테이블에
  즉시 한 행씩 쌓인다 — `Payment`를 거치지 않고 참여 자체가 이 테이블만으로 확정된다(결제는 참여와 별도 흐름,
  `checkout.html`로 이어짐).
- **참여 시각**: `TeamParticipation.joinedAt`(`@CreatedDate`, `NOT NULL`)이 이미 있다 — 새 컬럼 불필요.
- **팀장 여부**: `GroupBuyTeam.leader`(`member.id`)와 참여자의 `member.id`를 비교하면 판정 가능 — 별도 컬럼
  불필요.
- **기존 API**: `GET /api/products/{productId}/teams`/`POST .../teams`가 반환하는 `TeamResponse`는
  `leaderId`(숫자 id)만 내려주고, 개별 참여자 정보는 전혀 내려주지 않는다(`docs/api/team.md`). 참여자 목록을
  내려주는 엔드포인트는 현재 없음.
- **참여 취소/철회 시나리오 — 존재하지 않음(중요)**: 이 코드베이스에는 "팀이 아직 `RECRUITING`인 상태에서 개별
  참여자가 스스로 나가거나 결제를 취소하는" 기능이 없다(컨트롤러 전체에 leave/withdraw/cancel류 엔드포인트 없음
  확인). 팀 전체가 마감을 놓쳐 `FAILED`로 전환될 때만(`docs/dev/team/deadline-check/design.md`) 그 팀의 `PAID`
  결제들이 환불되는데, 이 시점엔 이미 팀이 `RECRUITING`이 아니라서(모집이 끝난 팀) "참가를 고민하는 구매자"가
  볼 필요가 없는 상태다. 게다가 `TeamParticipation`은 상태 컬럼이 없고 "하드 삭제 없음(참여 이력 영구 보존)"
  정책이라(`docs/db/team_participation.md`), 환불이 일어나도 그 행은 지워지거나 상태가 바뀌지 않는다 — 즉
  참여자 목록을 `TeamParticipation` 그대로 조회하는 것과 "환불된 사람 제외"는 애초에 서로 다른 문제다.
  **결론: 이번 스코프(모집 중인 팀의 참여자 목록)에서는 별도 제외 로직이 필요 없다** — `RECRUITING` 팀의
  `TeamParticipation` 행은 곧 현재 유효한 참여자 전원이다. (참고: 리더 본인이 결제를 완료하지 않고 방치하는
  경우처럼 참여 자체가 결제 없이도 성립하는 기존 갭이 있는데, 이건 이번 기능이 만든 문제가 아니라 이미 있던
  design.md 상의 흐름이라 스코프 밖으로 둔다.)
- **회원 식별정보 노출 전례**: 지금까지 실명(`Member.name`)이 API로 나가는 건 `MemberResponse`(로그인/내 정보
  조회, 본인에게만) 뿐이었다(`dto/MemberResponse.java`) — **다른 회원에게 누군가의 실명(또는 그 파생값)을
  보여주는 기능은 이번이 처음**이다. 마스킹을 하더라도 이 전례 없음은 리스크로 인지해야 한다.
- **프론트**: `product.html`의 "모집 중인 공구팀" 목록(`#team-list`) 안에 각 팀이 `team-item`(배지+인원수+참가
  버튼)으로 렌더링된다(`js/product.js:251-282`). 참여자 목록을 보여줄 자리는 이 `team-item` 안에 추가하는
  펼치기(토글) 영역이 자연스럽다 — 팀 목록을 불러올 때마다 모든 팀의 참여자를 한꺼번에 미리 불러오지 않고,
  사용자가 "참여자 보기"류 동작을 할 때만 개별 팀 단위로 조회하는 편이 낫다(팀이 여러 개일 때 목록 로드 시점에
  N개 팀 × 참여자 조회 요청이 동시에 나가는 걸 피함).

## 설계

### 표시 정보 (최종 결정)

- **마스킹된 실명** — `김**` 형태(첫 글자만 노출, 나머지는 글자 수만큼 `*`로 마스킹). 닉네임 필드는 아래
  "닉네임 트레이드오프" 결정에 따라 이번 스코프에서 추가하지 않는다.
- **참여 시각** — 정확한 시:분:초가 아니라 대략적인 단위(상대 시간 "N일 전" 또는 날짜 단위)로만 노출한다.
  서버는 기존 관례(`createdAt`/`deadline`처럼 ISO-8601 원본 시각)대로 `joinedAt`을 그대로 내려주고, 화면에
  "대략적으로만" 보여주는 건 프론트 표시 규칙으로 정한다(정확한 포맷 문자열은 Generate 재량).
- **팀장 여부** — 참여자가 그 팀의 리더인지(`isLeader`)를 함께 표시(예: "팀장" 배지).
- **노출하지 않는 것** — 실명 원문, 프로필 사진, 연락처(이메일/전화번호 등 자체가 없음), 회원 식별자
  (`memberId`). 참여자 상세를 클릭해 들어가는 기능이 없으므로(스코프 제외) 응답에 `memberId`를 포함할 필요가
  없다 — **응답에도 넣지 않는다**(불필요한 식별자 노출을 줄이는 방향).

#### 닉네임 필드 트레이드오프 및 추천

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A. 닉네임 필드 신규 추가 | `member.nickname`(nullable) 컬럼 추가 + 가입/설정 화면에서 입력받는 UI까지 구현 | 브랜드 뉴 nullable 컬럼이라 스키마 리스크는 낮음(`docs/db/member.md`의 `kakao_id` 전례처럼 `ddl-auto: update`가 안전하게 처리할 것으로 예상). 그러나 "회원이 닉네임을 설정하는 화면/플로우"까지가 필요해 **이번 기능(참여자 목록 표시)보다 훨씬 큰 스코프**(가입 폼, 마이페이지 프로필 수정, 검증 규칙 등)가 된다. |
| B. 닉네임 필드 없이 실명 마스킹 (추천) | 컬럼 추가 없이 기존 `name`을 읽기 시점에 마스킹해서 보여줌 | 스키마 변경 전혀 없음, 오늘 바로 구현 가능한 스코프. 다만 "마스킹된 실명"이 "자유롭게 정한 닉네임"보다 표현력이 떨어지고(같은 성씨는 다 비슷하게 보임), 진짜 닉네임 기능은 나중에 별도 기능(가입/프로필 확장)으로 다뤄야 한다. |

**추천: B안** — 이번 스코프는 참여자 목록 표시이지, 회원 프로필/닉네임 시스템 구축이 아니다. 닉네임은 나중에
별도 `docs/dev/ongoing/`(예: `member/profile` 개념)으로 다시 계획하는 걸 추천한다.

### API 계약

**신규 엔드포인트**를 추가한다(기존 `TeamResponse`에 필드를 얹지 않는다) — 팀 목록/신설 응답에는 참여자 배열이
필요 없고(목록 화면에서 매 팀마다 참여자까지 한꺼번에 실어 나르면 응답이 무거워지고 캐싱 특성도 달라짐), 사용자가
실제로 펼쳐볼 때만 개별 조회하는 편이 목록 조회 성능·트래픽 면에서 더 낫다.

- `GET /api/teams/{teamId}/participants` — 그 팀의 현재 참여자 목록
  - 경로 변수: `teamId`(Long)
  - 응답 `200 OK`: 참여자 배열, 각 항목은 `{ displayName, isLeader, joinedAt }` 형태(정확한 필드명/순서는
    Generate가 기존 DTO 네이밍 관례에 맞춰 정함)
  - 정렬: 팀장이 먼저, 이후 `joinedAt` 오름차순(참여한 순서)
  - 에러: `404 TEAM_NOT_FOUND`(존재하지 않는 팀) — 신규 에러코드 불필요, 기존 코드 재사용
  - **인증 필요 여부 — 결정 완료: 비로그인 공개(permitAll)**. 마스킹된 이름만 노출되고, 팀 목록의
    `currentCount`도 이미 비로그인에 공개돼 있어 같은 성격의 정보 등급으로 취급한다(사용자 결정, 2026-08-14).
    `SecurityConfig`에서 `GET /api/teams/{teamId}/participants`를 `permitAll`로 반영한다.

### 영향 계층

- **Repository**: `TeamParticipationRepository`에 팀별 참여자 목록을 회원 정보와 함께 한 번에 가져오는 조회
  추가(N+1 방지, `docs/code-convention.md` 기존 관례와 동일하게 fetch join). 정렬은 리더 우선 + `joinedAt`
  오름차순.
- **DTO**: 참여자 표시용 신규 response DTO 1개 추가(`displayName`/`isLeader`/`joinedAt`, 정확한 클래스/필드
  이름은 Generate).
- **Service**: `TeamService`(또는 별도 협업 서비스)에 팀 존재 검증(`TEAM_NOT_FOUND`) 후 참여자 목록을 위 DTO로
  매핑해 반환하는 메서드 추가. 마스킹 로직(첫 글자 노출+나머지 `*`)이 들어갈 위치도 이 계층.
- **Controller**: `TeamController`에 `GET /api/teams/{teamId}/participants` 추가.
- **Security**: 위 "확인 필요" 결정에 따라 `SecurityConfig`에 permitAll 여부 반영.
- **프론트**: `product.html`의 `team-item` 안에 참여자 목록을 펼쳐 보이는 UI 자리 추가, `js/product.js`에 그
  팀의 참여자를 조회해 렌더링하는 흐름 추가(펼칠 때 개별 조회, 마스킹된 이름·팀장 배지·대략적 참여 시각 표시).
  마크업 구조·펼치기 방식(버튼/토글 등)은 Generate 재량.

### 스코프 제외

- 참여자를 클릭해 상세 프로필을 보는 기능 — 제외(그럴 대상 정보 자체가 없음).
- 닉네임 필드/입력 UI 추가 — 제외(위 트레이드오프, B안 채택).
- 참여자 개별 목록에 페이지네이션 — 제외(팀 정원 자체가 작은 수, 기존 `mypage/view`의 "회원 개인 활동 규모라
  페이지네이션 예외" 선례와 동일한 근거).
- 팀 신설(`create`) 알림/실시간 브로드캐스트에 참여자 목록 변경 반영 — 제외(기존 실시간 메시징은 `currentCount`
  변경만 브로드캐스트한다, `docs/dev/team/crud/design.md`의 "스코프 한계" 참고. 이번 기능은 그 브로드캐스트를
  받으면 목록을 다시 그리는 기존 흐름에 얹혀가지 않고, 참여자 펼치기 영역은 사용자가 다시 펼칠 때 재조회하는
  것으로 충분하다고 본다 — 실시간으로 참여자 펼치기 화면까지 자동 갱신하는 건 이번 스코프 밖).
- `RECRUITING`이 아닌(`SUCCESS`/`FAILED`) 팀에 대한 참여자 조회 허용 여부 — 엔드포인트 자체는 상태와 무관하게
  `teamId` 존재만 확인하므로 자연히 동작하지만, 이 기능의 목적(참가 고민 지원)상 실제 UI 노출은 `RECRUITING`
  팀에서만 이뤄진다(기존 `GET /api/products/{productId}/teams`가 `RECRUITING`만 반환하는 것과 동일한 맥락).

## 데이터/스키마 변경

- **불필요**. `TeamParticipation.joinedAt`(참여 시각), `GroupBuyTeam.leader`(팀장 판정), `Member.name`(마스킹
  원본)까지 전부 기존 컬럼으로 충족된다. 신규 컬럼·테이블·마이그레이션이 없다 — 이 저장소가 `ddl-auto: update`
  + Railway 프로덕션 실데이터라는 전제(이전 조사에서 확인됨)에서 오는 리스크가 이번 기능에는 해당하지 않는다.

## 평가(통과) 기준

- 참여자가 있는 `RECRUITING` 팀에 대해 `GET /api/teams/{teamId}/participants` 호출 시 `200`, 응답 배열의
  각 항목이 마스킹된 이름 형태(`김**` 등, 실명 원문과 다름)·`isLeader`·참여 시각을 포함한다.
- 리더가 응답에서 `isLeader=true`로 정확히 표시된다.
- 정렬이 "리더 먼저, 이후 참여 순서" 규칙대로 나온다.
- 존재하지 않는 `teamId`로 호출 시 `404 TEAM_NOT_FOUND`.
- 응답에 실명 원문·`memberId`·이메일 등 식별정보가 포함되지 않는다(직접 assert).
- 비로그인 상태로 호출해도 `200`이 나온다(permitAll).
- N+1 없이 조회되는지(fetch join 사용) 코드 리뷰 또는 쿼리 카운트 검증.
- 프론트: `product.js`에서 팀 항목을 펼치면 참여자 목록이 그려지는지는 이 환경에 브라우저 자동화 도구가 없어
  코드 레벨(요청 흐름) 검증까지만 가능 — 실제 화면 확인은 사용자가 수동으로 확인 필요(기존 실시간 메시징
  기능 때와 동일한 한계, `docs/dev/team/crud/design.md` 참고).
- `./gradlew test` 전체 통과.

## 리스크 / 전제

- **전례 없는 정보 노출 성격**: 마스킹하더라도 "다른 회원과 관련된 정보를 다른 사용자에게 보여주는" 게 이
  코드베이스에서 처음이다(지금까지 실명은 본인 조회에만 쓰였음, `MemberResponse`). 이후 유사 기능(리뷰
  작성자 표시 등)이 생기면 이번에 정한 마스킹 규칙을 참고점으로 삼을 수 있다.
- **이름 1글자 등 짧은 이름의 마스킹 처리**: `첫 글자 + 나머지 글자 수만큼 *` 규칙을 이름이 1글자인 극단
  케이스에 그대로 적용하면 실질적으로 마스킹 효과가 없을 수 있다(전체가 그대로 노출됨) — 흔한 케이스는
  아니지만 존재 가능성 자체는 있다. 구체적 처리(예: 최소 마스킹 보장)는 Generate가 정한다.
- **참여=결제 완료가 아님(기존 갭, 이번이 만든 문제 아님)**: `TeamParticipation`은 결제 여부와 무관하게
  참가 시점에 즉시 생성된다 — 이번 참여자 목록은 "결제까지 마친 사람"이 아니라 "참가 액션을 한 사람" 전원을
  보여준다. 이 구분은 기존 설계에 이미 있던 것이고, 이번 기능이 새로 만들거나 악화시키는 문제는 아니다.
- **개별 참여 철회 기능이 향후 추가되는 경우의 의존성**: 지금은 개별 참여자가 스스로 나가는 기능이 없어서
  이번 참여자 목록이 항상 최신 상태를 반영하지만, 나중에 그런 기능이 생기면(예: 참가 취소) `TeamParticipation`에
  상태 컬럼이나 삭제 정책이 함께 추가되지 않는 한 이번 조회 로직도 같이 갱신해야 한다 — 지금 스코프에서는 그런
  기능이 없으므로 대응하지 않지만, 리스크로 기록해둔다.
