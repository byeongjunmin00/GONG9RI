# 공구 참여 결제 강제 + 미결제 자동 만료 + 상품 페이지 참여 취소

대상: team/crud(확장), team/reservation-expiry(신규)
담당: 전용운

## 배경 / 요구

사용자가 실사용 중 발견한 3가지 증상:

1. 공구 참여/신설을 눌러도 결제가 강제되지 않는다 — 성공 배너의 "결제하러 가기" 링크를 무시해도,
   혹은 체크아웃에서 "취소하기"를 눌러도 이미 팀 참여자로 남는다.
2. 상품 상세 페이지에서는 참여 취소가 불가능하고 마이페이지에서만 가능하다.
3. 참여 취소 시 환불 신청이 자동 생성돼야 하는데 구매자 환불내역에 아무것도 안 남는다.

원인 조사 결과, `TeamService.join()`/`create()`는 결제 여부와 무관하게 즉시 `TeamParticipation`을
만들고 `currentCount`를 올린다(`TeamService.java`). 결제는 완전히 별개 흐름(`checkout.html`)이고,
체크아웃의 "취소하기"는 API 호출 없이 그냥 뒤로 돌아간다(`checkout.js`). 그 결과 사용자는 결제 없이도
참여자로 남고(①), 이 상태에서 마이페이지로 취소해도 `PAID` 결제가 없어 `TeamService.leave()`의 환불
요청 생성 조건을 만족하지 못해 환불 요청이 안 생긴다(③). ②는 별개의 UI 누락(상품 페이지 팀 목록에
취소 버튼 자체가 없음).

세 증상 모두 "참가/신설이 결제 완료 여부와 무관하게 즉시 확정된다"는 하나의 근본 원인으로 수렴한다.

사용자와 논의해 정한 방향: **"예약 후 유예" 모델** — 참가/신설 시 자리는 지금처럼 즉시 반영하되,
결제 페이지로 강제 이동시키고, 결제를 마치지 않고 이탈하면(취소 버튼 클릭 또는 10분 무응답) 자동으로
자리를 반환한다.

## 설계

1. **강제 이동**: 참가/신설 성공 시, 지금처럼 배너만 띄우는 대신 결제 페이지
   (`checkout.html?productId=...&teamId=...`)로 자동 이동시킨다.
2. **명시적 취소 = 즉시 반환**: 체크아웃 화면의 "취소하기"와, 신규로 추가할 상품 페이지의 "참여 취소"
   버튼 모두 기존 `POST /api/teams/{teamId}/leave`를 그대로 재사용한다. 이 엔드포인트는 이미 결제
   유무에 따라 환불 요청 생성 여부를 올바르게 분기하므로 서버 로직 변경이 필요 없다.
3. **무응답 이탈 대비 자동 만료**: 참가/신설 후 **10분** 안에 그 참여에 연결된 결제가 `PAID`로
   확정되지 않으면, 예약을 자동으로 취소해 자리를 반환한다. `team/deadline-check`가 쓰는 "스캔 →
   이벤트 발행 → 팀 row 비관적 락 재사용" 패턴을 그대로 재사용하는 방향으로 접근한다(정확한 스케줄
   주기·구현 방식은 Generate 재량).
4. **상품 페이지 참여 취소 버튼 노출 조건**: 로그인한 사용자가 그 팀에 이미 참여 중인지 판별할 정보가
   프론트에 없다. `GET /api/products/{productId}/teams`(및 팀 신설 응답)에 요청자 기준
   `joinedByCurrentMember`(boolean) 필드를 추가한다 — 다른 참여자의 신원은 그대로 비공개(기존 마스킹
   원칙 유지), 오직 "나 자신의 참여 여부"만 노출하는 것이라 기존 프라이버시 설계와 충돌하지 않는다.
   비로그인 요청이면 `false`.

## 평가(통과) 기준

- 참가/신설 성공 시 수동 클릭 없이 결제 페이지로 이동한다.
- 결제 페이지 "취소하기" → 팀 참여가 즉시 취소되고(정원 감소·필요 시 리더 승계/FAILED 전환), 재조회
  시 참가 전 상태와 동일하다.
- 결제 미완료 상태로 10분 경과 → 스케줄러가 자동으로 해당 참여를 취소한다(수동 개입 없이).
- 결제를 완료(`PAID`)한 뒤 참여를 취소하면(상품 페이지든 마이페이지든) 환불 요청이 자동 생성되고
  `GET /api/buyer/mypage/refund-requests`에 나타난다.
- 상품 페이지에서 이미 참여 중인 팀은 "참가하기" 대신 "참여 취소"가 보이고 정상 동작한다.
- 기존 `team/crud` 동시성·실시간 브로드캐스트·트래픽 제어 테스트가 회귀 없이 통과한다(`./gradlew test`).

## 리스크 / 전제

- 10분 유예 동안 미결제자가 자리를 계속 점유한다 — 그사이 다른 사람은 여전히 `TEAM_FULL`을 만날 수
  있다(사용자 확인 후 수용된 트레이드오프).
- `TeamResponse`에 필드가 추가되면 이 API의 기존 소비자(있다면)에 영향 가능 — 다만 필드 추가만이라
  하위 호환.
- 로컬 검증에는 MySQL·Redis가 둘 다 필요하고, PortOne 결제 자체(샌드박스)까지 확인하려면 `.env`의
  `PORTONE_API_SECRET` 등이 있어야 한다(기존에 이미 있는 제약, `AGENTS.md` 참고).

## 영향 범위

- **service**: `TeamService`(스케줄러가 재사용할 수 있게 취소 로직 정리), 신규 서비스/스케줄러(가칭,
  `team/deadline-check`와 동일 패턴)
- **dto**: `TeamResponse`(`joinedByCurrentMember` 필드 추가)
- **controller**: `TeamController.list()`가 선택적 인증 정보를 받도록
- **프론트**: `product.js`(강제 이동, 참여 취소 버튼), `checkout.js`(취소 시 `leave` 호출)
- **문서**: `docs/api/team.md` 갱신, 완료 후 `docs/dev/team/crud/design.md` 갱신 + 신규
  `docs/dev/team/reservation-expiry/design.md` 생성
