# 공구팀 참여 취소 + 결제 환불 요청/승인

대상: refund/request (주, 신규 개념), team/leave (부, 신규 기능)
담당: 전용운

## 배경 / 요구

지금까지 환불은 "공구팀이 마감까지 미성사(FAILED)됐을 때 시스템이 자동으로 전액 환불"하는
경로(`team/deadline-check` → `payment/portone`의 `PaymentRefundService`)만 있었다
(`docs/dev/payment/portone/design.md` — "다루지 않는 것"에 "사용자 자발적 결제취소"가
스코프 밖으로 명시돼 있었음). 이번 요구는 그 스코프를 두 가지로 확장한다.

1. **공구팀 참여 취소**: 구매자가 모집 중인(`RECRUITING`) 공구팀에서 본인 참여를 취소할 수
   있게 한다. 팀이 이미 정원을 채워 `SUCCESS`로 전환된 뒤에는 취소할 수 없다(사용자 표현
   "본인 포함해서 1명 모자랄 때까지만" = `status == RECRUITING`일 때만).
2. **결제 완료 건 환불 요청**: 팀 없이 혼자 구매(솔로 구매)한 `PAID` 결제에 대해 구매자가
   환불을 요청하고 판매자가 승인/거절할 수 있게 한다(이미 배송됐을 수도 있어 판매자 검토가
   꼭 필요하다는 게 사용자 확인 사항).

사용자와 확인해 확정한 규칙:

- **참여 취소 시 정원 자리는 요청 즉시 반환**된다 — 취소 클릭 즉시 `current_count`가 줄고
  참여자 목록에서 빠져 다른 사람이 바로 그 자리에 참가할 수 있다. 실제 돈이 오가는 환불
  자체는 별도로 "요청됨" 상태로 남아 판매자 승인을 기다린다(자리 반환과 환불 승인은
  분리된 절차).
- **환불 승인은 기본적으로 판매자의 수동 승인이 필요하다**(휴먼 게이트 — 돈이 실제로
  오가는 절차라 자동 승인을 기본으로 두지 않음). 다만 **판매자가 상품별 설정에서
  "참여 취소 시 자동 환불" 체크박스를 켜두면**, 참여 취소로 발생한 환불 요청은 승인
  절차 없이 즉시 처리된다.
- **솔로 구매(팀 없이 혼자 구매) 건 환불 요청은 항상 판매자 승인/거절이 필요하다**(자동
  환불 설정 대상 아님 — 이미 배송됐을 수 있어서). **거절 시에는 자유 텍스트가 아니라
  몇 가지 정해진 사유 템플릿 중 하나를 선택**하게 한다(정확한 템플릿 문구는 Generate가
  정한다).
- **팀 구매 건은 팀이 정원을 채워 `SUCCESS`로 전환된 뒤에는 어떤 경로로도 환불이 불가능
  하다**(사용자 확인 — 악용 방지: 예를 들어 2인 목표 팀에 한 사람이 계정 2개로 결제한
  뒤 하나만 환불하면, 실질적으로 1인 결제인데 2인 구간 할인가로 사는 셈이 되기 때문).
  즉 팀 결제 건의 환불은 **오직 "A. 참여 취소"(팀이 아직 `RECRUITING`일 때만 가능) 경로
  하나뿐이며**, 아래 "B. 직접 환불 요청"은 **솔로 구매(`payment.team == null`) 건에만
  적용된다** — 팀이 딸린 결제는 직접 환불 요청 대상에서 제외한다.
- **공구팀 리더가 참여를 취소하면, 리더 지위는 그다음으로 먼저 참가한 참여자에게
  승계된다**(리더는 "방 구별용" 역할일 뿐 특별한 권한을 갖지 않는다는 사용자 확인 —
  리더가 나가도 팀 자체는 그대로 유지되고 계속 모집한다).
- **"팀 성사 후 환불 불가"는 구매자가 느끼기에 민감한 제약이라, 팀 신설/참가 시점에
  구매자가 이 사실을 명확히 인지하고 넘어가도록 한다**(사용자 확인 사항) — 그냥 작은
  안내 문구로 끝내지 않고, 체크박스 등으로 **명시적으로 확인해야만 신설/참가 버튼이
  눌리게** 한다(정확한 문구/UI는 Generate가 기존 스타일에 맞춰 정한다. 아래 "C" 참고).

## 설계

### A. 공구팀 참여 취소 (team/leave)

- 참여 취소는 `team/crud`의 `join()`과 대칭적인 새 API로 접근한다 — 팀 row에 락을 거는
  방식(현재 `lock` 전략과 동일한 접근)으로 동시성을 제어하는 방향. 취소 가능 조건: 로그인한
  `BUYER`가 그 팀의 현재 참여자여야 하고, 팀 상태가 `RECRUITING`이어야 한다(그 외 상태는
  거절).
- 취소가 성공하면 한 트랜잭션 안에서: 참여 기록 제거, 정원(`current_count`) 감소, 취소한
  사람이 리더였다면 리더를 그다음으로 먼저 참가한 참여자에게 승계. **팀에 아무도 안 남으면
  (마지막 한 명이 취소)** 그 팀은 더 이상 유지할 수 없으므로 `FAILED`로 전환한다(전제 —
  `team/deadline-check`의 자동실패 전환과 같은 성격, 이 경우 남은 결제가 없으므로 별도
  환불 대상도 없다).
- 이 취소로 인해 다른 사용자들이 보고 있는 화면의 정원 표시가 즉시 갱신돼야 하므로, 기존
  `team/crud`의 실시간 브로드캐스트(`TeamCapacityChangedEvent` → `/topic/products/{id}/teams`)
  메커니즘을 참여 취소에도 그대로 재사용하는 방향으로 간다.
- 취소한 사람이 그 팀에 대해 `PAID` 상태 결제를 갖고 있으면(아직 결제 전/실패 상태면 환불
  대상 자체가 없음), 아래 "B. 환불 요청/승인"의 요청을 자동으로 생성한다.

### B. 결제 환불 요청/승인 (refund/request, 신규 개념)

- 신규 개념으로 독립시킨다(`docs/dev-doc-guide.md`의 "cross-cutting 기능은 최상위 개념으로
  승격" 원칙 그대로 — 환불 요청이 team/payment 양쪽에 걸치기 때문에 `refund/`라는 이름으로
  이미 정책 문서(`docs/policy/refund-trigger.md`)에도 쓰이고 있는 이름을 그대로 이어받는다).
- 요청 생성 경로는 두 가지이며 서로 겹치지 않는다: (1) 위 A의 참여 취소가 자동으로 생성하는
  요청(팀 결제 전용, 사유 입력 없음 — "참여 취소"가 곧 사유), (2) 구매자가 솔로 구매
  (`payment.team == null`) 건에 대해 직접 요청(사유 입력 필요). **팀이 딸린 결제는 (2)의
  대상이 아니다** — 팀 결제의 환불은 오직 (1)로만 일어난다.
- 요청은 대기 상태로 남아 있다가, 판매자가 승인하거나(A에서 자동 환불 설정이 켜진 경우는
  승인 절차 생략) 거절할 수 있다. 승인되면 **기존 `PaymentRefundService`의 PortOne 결제취소
  실행 경로를 그대로 재사용**한다(이미 검증된 취소 API 호출·상태 전이·환불 알림 발행 로직을
  새로 만들지 않고 그대로 탄다) — 승인이라는 새 트리거만 추가되는 셈. 거절되면 결제는 `PAID`
  그대로 유지되고, 거절 사유(템플릿)가 요청 기록에 남아 구매자가 확인할 수 있다.
- 판매자의 승인/거절 화면, 구매자의 "환불 요청하기"·요청 상태 확인 화면이 필요하다(마이페이지
  하위 기능으로 자연스럽게 들어가는 방향 — 기존 알림 조회가 마이페이지 컨트롤러에 자연스럽게
  얹힌 것과 같은 패턴).
- **판매자별 "참여 취소 시 자동 환불" 설정은 상품 단위로 둔다**(계정 전체 설정이 아니라
  상품 등록/수정 폼에 체크박스 하나 추가) — 이 프로젝트가 가격 구간 등 판매 정책을 이미
  상품 단위로 관리하고 있는 것과 일관된 선택.

### C. 구매자 환불 불가 안내 (신설/참가 시점 명시적 확인)

- 상품 상세 페이지(`product.js`/`product.html`)에서 "신규 팀 신설하기"/"기존 팀 참가하기"를
  누르기 전에, "공구팀이 정원을 채워 성사되면 이후에는 환불이 불가능합니다"라는 안내를
  구매자가 **명시적으로 확인해야만**(체크박스 등) 진행되게 한다 — 단순 안내 문구만 붙이는
  것으로는 부족하다(사용자 확인 사항, 민감한 제약이라 인지 확인 절차 필수).
- 기존 `product.js`가 이미 "목표 인원(라디오)을 고르기 전까지 신설 버튼을 비활성 상태로
  두는" 가드 패턴을 쓰고 있으니(현재 `renderTargetParticipantsOptions`/
  `selectedTargetParticipants`), 이 확인 체크박스도 같은 방식(체크 전까지 버튼 비활성)으로
  자연스럽게 얹는 방향으로 간다. 정확한 문구/배치는 Generate가 기존 스타일에 맞춰 정한다.

## 평가(통과) 기준

- 참여 취소: `RECRUITING` 상태에서만 성공, `SUCCESS`/`FAILED` 상태에서는 거절되는지 테스트로 확인
- 취소 즉시 `current_count` 감소 + 참여자 목록에서 제거되고, 다른 사용자가 그 자리에 바로
  참가 가능한지 확인
- 리더가 취소하면 다음 최초 참가자에게 리더가 승계되는지, 마지막 한 명이 취소하면 팀이
  `FAILED`로 전환되는지 확인
- 참여 취소로 `PAID` 결제가 있으면 환불 요청이 자동 생성되는지, 없으면 생성되지 않는지 확인
- 판매자가 환불 요청을 승인하면 실제 PortOne 취소 경로(테스트에서는 `PortOneClient` mock)를
  타고 결제가 `REFUNDED`(또는 비동기면 `REFUND_PENDING`)로 전환되는지 확인
- 판매자가 거절하면 결제가 `PAID` 그대로 유지되고 거절 사유가 남는지 확인
- 상품별 자동 환불 설정이 켜져 있으면 참여 취소로 생긴 요청이 승인 없이 즉시 처리되는지,
  꺼져 있으면 대기 상태로 남는지 확인
- 솔로 구매 건은 직접 환불 요청 가능하고 항상 승인/거절 절차를 거치는지 확인
- **팀이 딸린 결제는 직접 환불 요청 API 자체가 거절되는지**(팀 결제의 환불은 오직 참여
  취소 경로로만 가능해야 함) 확인
- 본인 소유가 아닌 결제/팀에 대한 취소·환불 요청 시도가 거절되는지(403/404) 확인
- 팀 신설/참가 화면에서 "환불 불가" 확인 체크박스를 누르지 않으면 버튼이 비활성 상태로
  남아있는지 확인
- `./gradlew test` 전체 통과

## 리스크/전제

- **팀 결제는 `SUCCESS` 전환 이후 어떤 경로로도 환불 불가**(사용자 확인, 악용 방지 —
  위 "설계" 참고). 결과적으로 목표 인원이 채워지는 순간(마지막 참가자의 `join()` 호출
  시점) 그 팀에 속한 모든 결제는 이후 영구히 환불 요청 대상에서 제외된다 — 아직 결제를
  안 끝낸 마지막 참가자가 뒤늦게 결제를 완료해도(이미 `SUCCESS`인 팀에 대한 결제) 그
  결제 역시 환불 요청이 불가능하다는 뜻이다. 이건 의도된 동작이다.
- 참여 취소로 마지막 한 명이 빠져 팀이 `FAILED`로 전환되는 경우는 남은 결제가 없다는 전제
  하에 설계했다(취소한 사람의 결제는 위 환불 요청 절차로 별도 처리되므로 시점상 문제 없음).
- 동시성: 참여 취소도 `join()`처럼 팀 row에 대한 동시 접근(취소와 동시에 다른 사람이 참가
  시도하는 등)이 가능해 락 등 동시성 제어가 필요하다(현재 락 없음, 구체적 방식은 Generate가
  결정).
