# 애플리케이션 시간대 고정 (infra/timezone) — Design

## 개요

이 프로젝트는 시간을 전부 `LocalDateTime`(시간대 정보 없음)으로 다룬다. 그러면 **"이 값이 어느 시간대인지"는 JVM 기본 시간대가 결정**한다. 배포 환경(Railway 컨테이너)의 기본이 UTC라 한국 사용자가 보는 시각과 9시간 어긋나 있었다.

`Asia/Seoul`로 고정한다.

## 왜 문제였나 — 표시뿐 아니라 판정 로직도 틀렸다

**① 표시가 9시간 어긋남**

서버는 `2026-08-20T11:35:34`처럼 **시간대 표시가 없는** 문자열을 내려준다. 브라우저의 `new Date(...)`는 시간대가 없는 ISO 문자열을 **로컬 시각으로 해석**하므로, UTC 11:35에 만들어진 알림이 "오전 11:35"로 보인다 — 실제로는 KST 20:35였다.

**② `openAt` 판정이 틀림 (더 심각)**

```java
public boolean isNotYetOpen() {
    return openAt != null && openAt.isAfter(LocalDateTime.now());
}
```

판매자는 상품 공개 시각을 **브라우저에서 한국 시간으로** 입력하는데, 비교 대상인 `now()`는 UTC였다. 그래서 "9월 1일 0시 공개"로 설정한 상품이 **실제로는 오전 9시에 열렸다.** 표시 문제가 아니라 기능이 틀린 것이다.

## 어떻게

`TimeZoneConfig`의 `@PostConstruct`에서 `TimeZone.setDefault(Asia/Seoul)`.

**왜 Dockerfile JVM 옵션이나 Railway 환경변수가 아닌가** — 그 방식은 **배포 환경에만** 적용돼 로컬 개발·CI(UTC 러너)와 동작이 달라진다. "여기선 되는데 저기선 안 되는" 문제가 시간 관련 버그에서 특히 찾기 어렵다. 애플리케이션 코드에서 고정하면 어디서 실행하든 동일하고, 테스트로 회귀도 막을 수 있다.

## DB에는 UTC로 저장되고, 읽을 때 KST로 되돌아온다

**처음엔 "`DATETIME` 컬럼이라 드라이버 변환이 없다"고 판단했는데 틀렸다.** 실측으로 확인한 실제 동작은 이렇다.

```
앱(KST) 21:37 → [드라이버 변환] → DB 저장값 12:37 (UTC)
DB 12:37 (UTC) → [드라이버 변환] → API 응답 21:37 (KST)
```

JDBC URL의 `serverTimezone=UTC`가 "이 연결의 세션 시간대는 UTC"라고 알려주기 때문에, 드라이버가 **쓸 때 JVM 시간대 → UTC, 읽을 때 UTC → JVM 시간대**로 양방향 변환한다. 즉 **DB에는 UTC로 저장되지만 애플리케이션이 주고받는 값은 항상 KST**다.

이 구조는 오히려 바람직하다 — 저장은 시간대 중립(UTC), 표현은 서비스 시간대(KST)로 분리된다.

## 알려진 영향 — 기존 데이터

**기존 행도 함께 교정된다.** 이전 데이터는 UTC로 저장돼 있는데 이제 읽을 때 KST로 변환되므로, **예전 알림·상품도 올바른 시각으로 표시된다.** 별도 데이터 보정이 필요 없다.

(변경 전에는 JVM도 UTC라 UTC→UTC로 변환이 없었고, 그렇게 읽은 값을 브라우저가 로컬 시각으로 해석해서 9시간 어긋나 보였다.)

## 검증

`TimeZoneConfigTest` — 기본 시간대가 `Asia/Seoul`인지 단언. **CI 러너가 UTC라, 설정이 코드에 없으면 이 테스트가 실패한다** — "배포 환경에만 설정하고 코드엔 없는 상태"를 잡아내는 게 목적이다.

실제로 `TZ=UTC`로 강제한 환경에서 설정 제거 시 FAIL, 설정 복구 시 PASS를 확인했다.
