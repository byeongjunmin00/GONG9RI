# 애플리케이션 시간대를 Asia/Seoul로 고정

대상: infra/timezone
담당: 민병준

## 배경 — 사용자 리포트

> "알림 벨들이나 이거 날짜는 맞는데 시간이 틀린데?"

## 진단

실측으로 확인했다.

```
지금 KST 21:30 / UTC 12:30
프로덕션이 내려준 createdAt: 2026-08-20T11:35:34   ← UTC 기준
```

서버가 **시간대 표시 없는** `LocalDateTime`을 내려주고, 브라우저는 그런 문자열을 **로컬 시각으로 해석**한다. 그래서 9시간 어긋났다.

**그리고 표시만의 문제가 아니었다.** `Product.isNotYetOpen()`이 판매자가 한국 시간으로 입력한 `openAt`을 UTC인 `now()`와 비교해서, "9월 1일 0시 공개" 상품이 실제로는 오전 9시에 열리고 있었다.

원인: Dockerfile에 시간대 설정이 없어 Railway 컨테이너 기본값(UTC)으로 동작.

## 변경

`TimeZoneConfig`(`@PostConstruct`)에서 기본 시간대를 `Asia/Seoul`로 고정. 배포 환경에만 적용되는 방식(Dockerfile JVM 옵션, Railway 환경변수)을 쓰지 않은 이유는 `design.md` 참고.

## 검증

- **초기 판단 정정**: 처음엔 "`DATETIME` 컬럼이라 드라이버 변환이 없다"고 봤으나 실측 결과 틀렸다.
  JDBC URL의 `serverTimezone=UTC` 때문에 드라이버가 양방향 변환한다 —
  `앱(KST) 21:37 → DB 12:37(UTC) → API 응답 21:37(KST)`로 왕복이 일치함을 실서버로 확인했다.
  결과적으로 **기존 데이터도 함께 교정된다**(UTC로 저장된 값이 읽을 때 KST로 변환되므로)
- `TimeZoneConfigTest` 신규. **`TZ=UTC` 환경에서 설정 제거 시 FAIL / 복구 시 PASS를 실제로 확인**(테스트가 이 설정을 진짜로 지키는지 역검증)
- `./gradlew test` **409케이스 통과**

## 배운 것

**`LocalDateTime`만 쓰면 "어느 시간대인지"가 코드 어디에도 안 적힌다.** 그 정보가 JVM 기본값이라는 암묵적 전역 상태에 숨어 있어서, 로컬(KST)에서는 멀쩡하고 배포(UTC)에서만 틀리는 형태로 나타났다. 사용자가 "시간이 틀리다"고 알려주기 전까지 아무 테스트도 이걸 잡지 못했다 — 모든 테스트가 같은 시간대 안에서 일관됐기 때문이다.
