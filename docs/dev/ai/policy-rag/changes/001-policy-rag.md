# 정책 문서 RAG 검색 인터페이스 (구매자 챗봇 연동용)

대상: ai/policy-rag                 <!-- 완료 시 이 기능의 changes/로 이동 -->
담당: 전용운

## 배경 / 요구

발제 AI 필수 두 번째 기능(구매자 챗봇: Tool Calling / 장애격리·비용인식 / SSE 스트리밍 / RAG)은 민병준이 담당한다(`docs/dev/ai/product-suggestion/changes/001-product-suggestion.md` 참고). 그중 **RAG(검색) 부분만 전용운이 먼저 인터페이스 + 구현체로 분리**해서 만들어 둔다. 챗봇 본체(대화 오케스트레이션·Tool Calling·SSE 스트리밍)는 민병준이 별도로 만들며, 완성되면 이 인터페이스를 주입받아 "정책 관련 질문에 답할 근거 문맥"을 가져오는 용도로 쓴다.

## 설계

- **검색 대상**: `docs/policy/refund-trigger.md`(환불 트리거) + `docs/policy/team-success-criteria.md`(공구팀 성사 판정 기준) — 구매자가 실제로 물어볼 만한 고객향 정책만 포함한다.
  - `docs/policy/caching.md`(캐싱 정책)는 **의도적으로 제외**한다. 서버 내부 성능 정책이라 고객 질문과 무관하고, 벡터 검색 특성상 애매한 질문에 잘못 매칭되면 TTL·Redis 등 내부 구현 용어가 챗봇 답변에 노출될 위험이 있다.
  - 정책 문서가 SSOT이므로, 앱이 기동 시 참조할 수 있는 형태로 반입한다(정확한 반입 방식은 Generate에서 결정).
- **벡터 검색**: Spring AI 내장 `SimpleVectorStore`(인메모리) — 별도 벡터 DB/인프라 추가 없이 가볍게 구성한다. 임베딩은 이미 의존성에 있는 `spring-ai-starter-model-openai`의 `EmbeddingModel` 사용(저비용 임베딩 모델 사용 방향 — `product-suggestion`에서 지킨 비용 인식 원칙과 동일).
- **색인 단위**: 대상 정책 문서 2개가 이미 짧으므로 파일 단위(또는 규칙/근거/적용대상 섹션 단위) 청크로 시작한다 — 스플리터 세부 구현은 Generate에서 결정.
- **연결 방식**: REST 엔드포인트 없이 같은 스프링 컨텍스트 안에서 **인터페이스 + 구현체**를 두고 생성자 주입으로 연결한다(`docs/code-convention.md` 생성자 주입 원칙). 정확한 인터페이스 메서드 시그니처(입력: 사용자 질의 문자열 / 출력: 관련 정책 스니펫 목록 — 정도만 계약)는 Generate에서 확정한다.
- **범위**: 이번 계획은 "검색(retrieval)"까지다. 최종 답변 생성·Tool Calling·SSE 스트리밍은 챗봇(민병준) 범위이며 이 계획에 포함하지 않는다.
- 새 REST 엔드포인트나 새 DB 테이블이 없다(인메모리 벡터스토어) → `docs/api/`, `docs/db/` 신규 작성 불필요.

### 설계 변경 (Generate 2회 시도 후, 2026-08-11 재승인)

Attempt 1~2에서 유사도 **threshold로 "관련 있음/없음"을 걸러내는 방식은 이 코퍼스 규모(정책 문서 2개, 6청크)에서 신뢰할 수 없음을 실측으로 확인**했다(`docs/logs/ai/policy-rag/001-policy-rag.md` 참고 — 임베딩 모델을 바꿔도 "환불"이란 단어를 안 쓴 자연스러운 패러프레이즈가 완전 무관한 질문보다 점수가 낮게 나오는 경우가 실제로 있었음). 이에 따라 설계를 다음과 같이 바꾼다:

- **필터링 포기, topK만 반환**: `findRelevantSnippets`는 항상 상위 K개 스니펫을 그대로 반환한다(빈 리스트를 반환하는 "관련 없음 판정"은 이 인터페이스가 하지 않는다).
- **관련성 최종 판단은 소비자(챗봇) 몫**: "제공된 문맥이 질문과 무관하면 참고하지 말고 무시하라"는 판단은 이 인터페이스를 호출하는 쪽(향후 `BuyerChatService`)의 시스템 프롬프트가 맡는다 — 민병준의 챗봇이 이미 같은 방식(환각 방어: "확인 안 된 사실을 지어내지 마라")을 쓰고 있어 자연스럽게 연결된다. **이 인터페이스 자체는 "관련 없는 내용을 안 섞는다"를 보장하지 않는다** — 이건 이번 계획의 통과 기준에서 뺀다.
- **패러프레이즈 보강(경량 완화책)**: 색인 시 각 정책 섹션에 자주 쓰일 법한 자연스러운 질문 예시를 몇 개 덧붙여서 함께 임베딩한다(예: 환불 규칙 섹션에 "제 돈은 언제 돌려받을 수 있나요?" 같은 예시 문구 추가). **원본 `docs/policy/*.md`는 건드리지 않고**, 색인 컴포넌트가 청크를 만들 때만 예시 문구를 덧붙인다(어디에 어떻게 덧붙일지는 Generate가 정한다). 이건 완전한 해결책이 아니라 **미리 예상한 흔한 표현만 보완**하는 것임을 명확히 인지한다 — 예상 못 한 표현은 여전히 놓칠 수 있고, 그 경우의 안전망은 위 챗봇 프롬프트 몫이다.

## 리스크 / 전제

- `docs/policy/` 원본과 앱에 반입된 색인용 콘텐츠가 어긋날 수 있다(정책 문서가 수정돼도 반입된 사본이 자동 갱신되지 않음 — 동기화 필요).
- 인메모리 벡터스토어라 서버 재시작마다 재색인이 필요하다(정책 문서가 적어 기동 시 재색인은 허용 가능하다고 가정).
- OpenAI 임베딩 API 호출이 추가로 발생한다(로컬 `.env`의 `OPENAI_API_KEY` 재사용 — 비용 인식 필요).
- 챗봇 본체(`BuyerChatService`)는 이미 존재하지만, 민병준이 RAG 훅은 의도적으로 비워뒀다(`docs/dev/ai/buyer-chatbot/design.md`: "나중에 이 서비스에 결합될 수 있으므로 ... 지금 RAG 훅은 만들지 않는다"). 이번 작업 범위는 검색 인터페이스까지이고, `BuyerChatService`에 실제로 연결하는 것은 별도 후속 작업이다 — 검증은 이 인터페이스 자체를 테스트/임시 호출로 한다.

## 평가(통과) 기준

- 정책 관련 질의(예: "환불은 언제 되나요?", "공구팀은 언제 성사되나요?", "공구 기한이 지나면 어떻게 되나요?") → 관련 정책 스니펫이 상위에 반환됨을 테스트로 확인.
- ~~무관한 질의 또는 캐싱·서버 내부 관련 질의에는 관련 없는 내용이 섞이지 않음을 정성 확인.~~ → **설계 변경으로 제외**(threshold 필터링을 포기했으므로 이 인터페이스가 보장하지 않음 — 위 "설계 변경" 참고). 대신: 무관 질의에도 topK개가 그대로 반환되는 것을 "의도된 동작"으로 확인(예외적으로 비거나 에러 나면 안 됨).
- **패러프레이즈 보강 확인**: 색인에 추가한 예시 표현과 비슷한 자연스러운 질문(예: "제 돈은 언제 돌려받을 수 있나요?")을 실제로 호출했을 때, 해당 정책 스니펫이 상위 결과에 포함되는지 실측 확인.
- `./gradlew build` 전체 통과(회귀 없음).
- 실제 OpenAI 임베딩 API 최소 1회 이상 실호출로 확인(로그 기록).
