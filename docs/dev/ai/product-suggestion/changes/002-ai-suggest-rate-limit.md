# 상품등록 도우미 트래픽 제어 추가 — AI 호출 경로의 마지막 갭

대상: ai/product-suggestion
담당: 민병준

## 배경

OpenAI를 호출하는 엔드포인트가 두 개인데(`POST /api/buyer/chat/messages`, `POST /api/seller/products/ai-suggest`) **한쪽만 트래픽 제어가 걸려 있었다.**

이 갭은 챗봇 rate limit을 추가하던 2026-08-19에 이미 발견해서 "여기도 같은 상황"이라고 짚어놨는데, 그때 함께 처리하지 않고 넘어간 것이다. 그 사이 상품등록 도우미의 방어선은 **판매자 로그인 게이트 하나뿐**이었다 — 로그인한 판매자 계정 하나만 있으면 스크립트로 무한 반복 호출이 가능했고, 호출마다 실제 비용이 나간다.

## 변경

`RateLimitFilter.RULES`에 규칙 추가 — 같은 클라이언트(IP)가 **1분에 5회** 초과 시 429.

### 한도를 챗봇(1분 10회)보다 낮게 잡은 이유

| | 챗봇 | 상품등록 도우미 |
|---|---|---|
| 사용 패턴 | 대화형 — 메시지 주고받으며 연속 호출이 자연스러움 | 상품 하나 등록 전에 초안을 받아보는 용도 — 연속 호출할 일이 적음 |
| 호출당 프롬프트 | 사용자 메시지 + 대화 이력 | 카테고리별 템플릿 전문 + 사용자 입력 → **더 길고 단가가 높음** |

정상 사용으로는 1분에 5회를 채울 일이 거의 없고, 스크립트 반복 호출은 확실히 막힌다.

## 검증

`AiSuggestRateLimitFilterTest`(신규 3케이스):

- 임계값(5회) 이내는 필터를 통과한다
- 6번째부터 429 `TOO_MANY_REQUESTS`
- **접두사가 같은 이웃 엔드포인트(`POST /api/seller/products`)는 대상이 아니다** — 정규식이 `ai-suggest`만 정확히 매칭하는지, 즉 과잉 차단이 없는지 함께 고정
- **규칙을 제거하면 실제로 실패하는 것까지 확인**했다(테스트가 이 변경을 진짜로 지키는지 역검증)

`BuyerChatRateLimitFilterTest`와 동일하게 **비로그인 요청**으로 검증한다 — `RateLimitFilter`가 Spring Security 필터체인보다 먼저 실행되므로 임계값 이내는 401(필터 통과 후 인증 단계에서 거절), 초과는 429(필터 자체에서 거절)로 갈린다. 덕분에 실제 OpenAI 호출이나 `ChatClient` 목 없이 필터 동작만 독립적으로 검증할 수 있다.

## 배운 것

**"여기도 같은 갭"이라고 발견해놓고 그 자리에서 처리하지 않으면, 그 상태가 그대로 남는다.** 챗봇 작업 중에 이미 알고 있었는데도 하루 넘게 한쪽만 막힌 채로 운영됐다. 같은 종류의 구멍을 발견했을 때는 그때 함께 닫거나, 최소한 명시적인 할 일로 남겨서 잊히지 않게 해야 한다.
