# 리뷰 작성 시 상품 캐시 무효화 (신뢰 배지 즉시 반영)

대상: product/seller-trust
담당: 민병준

## 배경 / 요구

사용자가 배포된 사이트에서 신뢰 배지를 눈으로 확인해보려고 `demo_seller` 계정으로 상품을 올리고, 서로 다른 구매자 3명으로 결제 후 5점 리뷰를 3개 채웠다. 조건(평균 ≥ 4.5, 개수 ≥ 3)을 완전히 만족했는데도 **배지가 안 떴다.**

## 진단

캐시 문제라고 단정하기 전에, 집계 로직 자체가 깨진 건지 캐시가 낡은 건지를 갈라내야 했다. 목록 캐시 키가 `page+size` 조합이라는 점을 이용해, **아무도 요청한 적 없는 size로 부르면 캐시 미스가 나서 방금 계산한 값이 나온다**는 걸 이용했다.

동일 상품, 동일 시점에:

| 요청 | `sellerTrustedBadge` |
|------|------|
| `size=37` (캐시 미스) | `true` |
| `size=41` (캐시 미스) | `true` |
| `size=50` (캐시 히트) | `false` |

리뷰 목록 API(`GET /api/products/33/reviews`, 캐시 안 탐)도 `{avg: 5.0, count: 3}`으로 조건 충족을 확인해줬다.

→ **집계 로직은 정상이고, 캐시에 낡은 `false`가 남아있는 것**으로 확정.

원인: `ReviewService`에 `@CacheEvict`가 하나도 없었다. 상품 목록·상세 캐시(TTL 30분)의 무효화 트리거가 `ProductService.register/update/delete`에만 걸려 있었다.

## 이게 "버그"인가 — 원래는 의도된 트레이드오프였다

`design.md`에는 배지 staleness가 **의도적으로 허용된** 것으로 적혀 있었다:

> 리뷰 평균은 사용자가 실시간으로 지켜보는 값이 아니라 참고 지표라, 최대 30분 낡아도 되는 신선도로 판단

그래서 단순한 "무효화 누락"이라기보다, 받아들였던 트레이드오프가 실제 사용 경험에서 안 맞았던 경우다. 다만:

- "조건을 만족시켰는데 아무 일도 안 일어난다"는 체감이 나쁘다 — 판매자 입장에선 기능이 고장난 것처럼 보인다.
- 리뷰 작성은 상품 조회에 비해 훨씬 드문 쓰기라, 무효화를 걸어도 캐시 적중률 손해가 사실상 없다.

→ 트레이드오프를 **바꾸기로** 결정. 배지를 캐시 안에 담는다는 원래 설계 결정 자체는 그대로 유지한다(캐시 밖 별도 조회를 만들지 않음).

## 설계

`ReviewService.create/update/delete`에 `@Caching(evict = {...})`로 상품 목록·상세 캐시를 무효화한다.

**상세 캐시를 `key = "#productId"`가 아니라 `allEntries = true`로 날린다.** 배지는 판매자의 *전체 상품* 리뷰를 합산해 판정하므로, 상품 A에 리뷰가 하나 달리면 같은 판매자의 상품 B·C의 배지까지 같이 바뀐다. 리뷰가 달린 상품 하나만 날리면 나머지가 낡은 값으로 남는다.

## 배운 것

캐싱 정책 표에 무효화 시점을 "해당 상품 수정·삭제 시"라고만 적어둔 게 이 누락의 뿌리였다. **캐시 키가 되는 엔티티(상품)와 캐시된 값이 실제로 의존하는 데이터(리뷰)가 다를 수 있다**는 걸 표가 표현하지 못했다. `docs/policy/caching.md`에 이 원칙을 명시해뒀다.

한편 TTL 30분은 설계 의도대로 최후 방어선 역할을 했다 — 무효화가 누락됐어도 값이 영구히 굳지는 않았다(`caching.md`의 "TTL은 최후 방어선" 항목).
