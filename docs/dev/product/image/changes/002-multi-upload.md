# 002 — 이미지 여러 장 + 파일 업로드 + 상세 갤러리

## 배경

사용자 리포트 3건이 하나로 이어졌다.

> "우리는 왜 사진이 한 장밖에 안 들어가?"
> "사진 아래가 텅텅 빈 게 좀 별로인 것 같아 … 슬라이드로 더 누를 수 있게도 가능하거나"
> "사진 올리는 것도 왜 URL로만 해야 하는 거야? 휴대폰으로 들어가면 사진 넣기도 너무 힘들고"

001에서 파일 업로드를 넣지 않은 이유는 **저장할 곳이 없어서**였다(컨테이너 파일시스템은 재배포 시 초기화). 그런데 **그 전제가 이미 깨져 있었다** — 프로젝트는 이미 Railway 볼륨을 Redis·MySQL에 쓰고 있었다. 볼륨을 하나 더 붙이면 추가 비용·외부 계정 없이 파일이 살아남는다.

## 결정

| 결정 | 근거 |
|---|---|
| S3/Cloudinary가 아니라 Railway 볼륨 | 추가 비용·계정·키가 없고 팀이 이미 이해하는 인프라. 대가는 CDN 없음 + 다중 인스턴스 확장 시 깨짐 — 알려진 한계로 명시 |
| `product.image_url`을 남기고 `product_image`를 추가 | 목록 화면이 상품마다 이미지 테이블을 조회하면 N+1. 대표 이미지 비정규화는 의도적 |
| 마이그레이션 없음 | `product_image`가 비면 `imageUrl` 한 장으로 폴백. **기존 상품 35개가 외부 URL(pexels)** 이라 하위호환이 설계 제약이었다 |
| 업로드 파일과 외부 URL을 구분하지 않음 | 화면·API는 "이미지 목록"만 알면 된다. 어느 쪽인지는 저장 계층의 관심사 |
| 저장 시 축소·재인코딩 | 원본 그대로면 상품 20개에서 볼륨이 찬다(계산). 부수효과로 EXIF 위치정보도 떨어진다 |
| 사진 1장이면 갤러리 UI를 전부 숨김 | 기존 상품이 이전과 똑같이 보여야 한다 |

## 검증

- `./gradlew test` 전체 통과(417). 업로드 테스트는 **거절 경로가 정상 경로보다 많다** — 확장자만 이미지인 파일, 경로 탈출 파일명, 크기 초과.
- 로컬 실측: 파일 3장 업로드 → 상세 응답에 순서대로, PNG가 JPEG로 재인코딩, 대표 이미지는 첫 장. `imageUrls` 없이 등록한 상품도 한 장짜리로 정상 노출(하위호환).
- 저장 크기 실측: 4000×3000 / 1.96MB → **1600×1200 / 498KB**.
- **프로덕션 볼륨 지속성 실측(2026-08-20)**: `/data/uploads`에 파일 기록(14:33:42 UTC) → 재배포 → 컨테이너 PID 1 시작 시각이 **14:34:28 UTC**로 바뀐 것(= 실제로 교체됨)을 확인 → 파일이 그대로 남아있음(14:35:16 UTC). *파일이 남아있다는 것만으로는 부족하다 — 컨테이너가 실제로 재시작됐는지를 같이 확인해야 검증이 성립한다.*
- 볼륨 실측: `/dev/zd3360`, 가용 **434MB**(할당 500MB).

## 함께 고친 버그

**용량 초과 업로드가 500으로 나가던 문제.** 5.5MB 사진으로 재현. 톰캣 multipart 파서가 컨트롤러 진입 전에 거절해서 `ProductImageStorage`의 5MB 검사가 도달하지 못하고, `MaxUploadSizeExceededException`이 catch-all로 흘러 500이 됐다. `IMAGE_FILE_TOO_LARGE`(400)로 맞췄고, 회귀 테스트는 실제 톰캣(`RANDOM_PORT`)을 띄운다 — MockMvc는 파서를 안 타서 **핸들러가 없어도 통과해버린다**.

## 남은 것 / 스코프 밖

- 이미지 자르기·회전, 드래그로 순서 변경
- CDN·오브젝트 스토리지
- 기존 외부 URL을 볼륨으로 옮기는 마이그레이션(그대로 두고 표시만 통합)
