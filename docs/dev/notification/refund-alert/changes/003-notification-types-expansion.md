# 알림 종류 확장 (notification/refund-alert)

담당: 민병준
대상 개념/기능: `notification/refund-alert` (기존 기능 확장, 신규 토픽 아님)

## 배경 / 요구

헤더 알림 벨 UI를 붙인 뒤 사용자가 실제로 써보고 지적했다.

> "알림 오는 것들이 너무 적지 않냐 이거야. 뭐 결제가 됐다는 둥 문의가 들어왔다는 둥 뭐 이런 알림들이 많이 있지 않냐?"

맞는 지적이다. `NotificationType`에 값이 **`TEAM_REFUNDED` 하나뿐**이라, 공구 플랫폼이면 당연히 와야 할 알림(공구 성사, 문의 답변, 환불 요청 접수 등)이 전부 없다. 벨을 만들어놨는데 채울 내용이 사실상 없는 상태다.

사용자와 범위를 확정했다 — **아래 8종 전부 추가**하고, 알림을 누르면 이동할 수 있게 **링크를 저장**한다.

## 무엇을 (범위)

### 추가할 알림 8종

**판매자 수신 (5종)**

| 알림 | 발생 시점 | 왜 필요한가 |
|---|---|---|
| 환불 요청 접수 | 구매자가 환불을 요청했을 때 | 판매자가 **승인/거절해야 하는 작업**인데 지금은 마이페이지를 직접 열어봐야만 안다 |
| 상품 문의 등록 | 내 상품에 문의가 달렸을 때 | 답변해야 하는 작업인데 모른다 (사용자가 직접 언급한 항목) |
| 결제 발생 | 내 상품이 결제됐을 때 | 주문 발생 (사용자가 직접 언급한 항목) |
| 공구팀 성사 | 내 상품의 공구팀이 정원을 채웠을 때 | 발송 준비가 필요한 시점 |
| 리뷰 등록 | 내 상품에 리뷰가 달렸을 때 | 평판 관리 |

**구매자 수신 (3종)**

| 알림 | 발생 시점 | 왜 필요한가 |
|---|---|---|
| 공구팀 성사 | 참여한 팀이 정원을 채웠을 때 | **공구 플랫폼의 핵심 순간인데 알림이 없다** — 가장 큰 구멍 |
| 문의 답변 등록 | 내 문의에 판매자가 답변했을 때 | 지금은 상품 페이지에 다시 들어가 확인해야 함 |
| 환불 요청 승인/거절 | 판매자가 내 환불 요청을 처리했을 때 | 결과를 알 방법이 없음 |

### 의도적으로 제외한 것

- **구매자의 "결제 완료" 알림** — 본인이 방금 한 행동이고 결제 완료 화면에 이미 표시된다. 알림으로 또 알리는 건 소음이다. (판매자의 "결제 발생"은 본인이 한 행동이 아니므로 포함)
- 이메일/푸시 등 **외부 발송 채널** — 기존과 동일하게 DB 저장 + 벨 UI 확인만. (SendGrid 연동이 있지만 인증 메일 용도이고, 알림마다 메일을 보내는 건 별개 스코프)

### 링크 저장

지금 `Notification`은 연결 대상이 `related_team_id`(공구팀) 하나뿐이라 문의·리뷰·결제 알림이 가리킬 곳을 표현할 수 없다. 사용자와 **"이동할 링크 자체를 저장"**하는 방식으로 확정했다(대안이던 `targetType`+`targetId` 정규화 방식은 프론트에 타입별 URL 조립 분기가 늘어나 제외).

기존 `related_team_id`는 제거하지 않고 유지한다(기존 데이터·기존 알림 로직 호환).

## 어떻게 (접근/설계 방향)

- **기존 알림 기능의 확장**이다. 새 개념/토픽을 만들지 않고 `notification/refund-alert`의 `design.md`·`NotificationService`·`NotificationType`을 넓힌다. (기능명이 `refund-alert`인데 환불 외 알림을 담게 되므로, 문서에 이름과 실제 범위가 어긋난다는 점을 명시한다 — 디렉터리 개명은 링크가 여럿 깨져 이번 스코프에서 제외)
- **알림 생성이 원래 작업을 방해하면 안 된다.** 알림을 만들다 실패했다고 결제·문의·환불 승인 같은 본 작업이 실패하면 안 되고, 반대로 본 작업이 롤백됐는데 알림만 남아도 안 된다. 기존 환불 알림이 이 제약을 이미 만족하는 구조로 돼 있으므로 같은 성질을 유지한다(구체 메커니즘은 Generate에서 결정).
- **수신자를 정확히 좁힌다.** 각 알림은 "그 일과 실제로 관련된 사람"에게만 간다 — 판매자 알림은 해당 상품의 판매자, 문의 답변 알림은 그 문의 작성자, 공구팀 성사 알림은 그 팀 참여자 전원.
- **자기 행동에 자기가 알림받지 않는다.** 예를 들어 판매자 본인이 자기 상품에 뭔가 했을 때 자기에게 알림이 가는 경우가 없도록 한다.
- **메시지 문구는 상수로 관리**한다(기존 환불 알림과 동일한 방식).

## 통과(평가) 기준

- `./gradlew test` 전체 통과.
- 알림 8종 각각에 대해, **발생 조건을 만족시키면 올바른 수신자에게만 알림이 생성되는지** 테스트로 검증한다(수신자를 잘못 잡는 게 이 기능의 핵심 리스크라 "생성됐다"가 아니라 "누구에게 생성됐는지"를 단언한다).
- 본 작업이 실패/롤백된 경우 알림이 남지 않는지, 반대로 알림 생성이 실패해도 본 작업은 성공하는지 확인한다.
- 기존 `TEAM_REFUNDED` 알림과 읽음 처리(개별/전체) 동작에 회귀가 없다.
- 프로덕션 배포 후, 실제로 알림 하나 이상을 발생시켜 벨에 뜨고 클릭 시 링크로 이동하는 것까지 확인한다.

## 리스크 / 전제

- **`ddl-auto: update`로 컬럼이 추가된다.** 기존 `notification` 행들은 링크가 NULL이 되므로, 프론트가 링크 없는 알림을 정상 처리해야 한다(현재 프로덕션에 이미 알림 데이터가 있는지와 무관하게 NULL 케이스는 반드시 존재할 수 있다).
- **Redis 캐시 DTO 아님** — `NotificationResponse`는 캐시 대상이 아니라, 예전 `sellerTrustedBadge`에서 겪은 "캐시된 옛 JSON 역직렬화 실패" 문제는 해당 없다. (확인 완료)
- **알림 개수가 갑자기 늘어난다.** 지금까진 사실상 알림이 거의 없었는데 8종이 붙으면 벨에 쌓인다. 현재 벨 UI는 전체 목록을 한 번에 불러와 그대로 뿌리는 구조라, 알림이 많아졌을 때의 노출 방식(개수 제한/더보기 등)이 적절한지 확인이 필요하다.
- **판매자 "결제 발생" 알림은 결제 확정 경로가 2개**다(클라이언트 confirm 호출 / PortOne 웹훅). 두 경로 모두에서 알림이 정확히 1번만 생기는지 주의가 필요하다(중복 알림 리스크).
- **공구팀 성사 알림은 참여자 전원 대상**이라, 정원이 큰 팀이면 한 번에 다수의 알림이 생성된다.
- 로컬 검증에 MySQL + Redis 가동 필요(기존과 동일).
- 팀원(전용운)이 같은 영역을 작업 중이지 않은 것을 `docs/dev/ongoing/` 확인으로 검증했다(현재 `design-system-sharp-ui.md`만 존재, 알림과 무관).

## 실행 결과

계획대로 8종 전부 구현하고 링크 저장까지 완료했다. 전체 379케이스 통과.

### 구조 — 이벤트를 하나로 통일

종류마다 이벤트+리스너를 한 쌍씩 만들면 보일러플레이트만 늘고 정작 하는 일(알림 row INSERT)은 전부 같아서, `NotificationRequestedEvent` 하나로 통일했다. 문구와 링크 규칙은 `NotificationPublisher` 한 곳에 모아, 각 도메인 서비스의 호출부는 한 줄로 유지된다.

기존 `TeamRefundedEvent`는 그대로 뒀다 — 그건 "환불이 완료됐다"는 도메인 사실을 알리는 이벤트라 알림 외의 구독자가 붙을 수 있는 반면, 새 이벤트는 처음부터 알림 전용이다.

### `@Async`가 필수였다 — 커넥션 풀 고갈을 실측으로 발견

계획에 없던 발견이다. 처음엔 기존 환불 알림과 똑같이 동기 `@TransactionalEventListener(AFTER_COMMIT)`로 만들었는데, 전체 테스트에서 `SellerRevenueSummaryConcurrencyTest`(동시 결제 20건)가 타임아웃으로 실패했다. 로그를 보니 원인이 명확했다:

```
HikariPool-6 - Connection is not available, request timed out after 30002ms
(total=10, active=10, idle=0, waiting=16)
```

**AFTER_COMMIT 콜백은 원본 트랜잭션의 JDBC 커넥션이 아직 반납되기 전에 실행된다.** 거기서 동기로 `REQUIRES_NEW` 서비스를 호출하면 한 요청 스레드가 커넥션을 **동시에 2개** 필요로 한다. 동시 요청이 풀 크기(10)만큼 몰리면 전원이 첫 커넥션을 쥔 채 두 번째를 기다리며 아무도 진행하지 못한다.

테스트 환경만의 문제가 아니라 **동시 결제가 몰리면 프로덕션에서도 그대로 재현될 결함**이었다(팀원이 앞서 고친 OSIV 커넥션 고갈과 같은 부류). `@Async`로 분리해 알림 INSERT가 별도 스레드에서 커넥션 1개만 잡게 해결했다 — `RefundRequestApprovedEventListener`가 이미 같은 이유로 `@Async`다.

트레이드오프: 알림이 원인 작업보다 아주 조금 늦게 보인다. 알림은 즉시성이 필수인 데이터가 아니라 허용 가능하다고 판단했고, 대신 테스트는 폴링으로 기다린다.

**`SellerRevenueSummaryConcurrencyTest`에서는 알림 발행기를 목으로 막지 않고 실제 경로를 그대로 뒀다** — `@Async`가 나중에 제거되면 이 테스트가 다시 잡아주는 회귀 테스트 역할을 하기 때문이다. (알림이 관심사가 아닌 다른 테스트들은 목으로 끊어 정리 로직과 비동기 경합을 피했다.)

### 계획에서 짚은 리스크 처리

| 리스크 | 결과 |
|---|---|
| 결제 확정 경로가 2개(클라이언트 confirm / 웹훅) → 중복 알림 | 두 경로가 모두 `applyVerificationResult`로 모이고 양쪽 호출부가 PENDING일 때만 도달하므로 여기서만 발행. **전용 테스트로 확인**(confirm 후 웹훅을 뒤늦게 호출해도 알림 1건) |
| 기존 알림은 링크가 NULL | 프론트가 링크 없는 알림을 "클릭해도 이동하지 않는 항목"으로 처리 |
| 메시지 길이 초과 | 상품명이 최대 100자라 가장 긴 문구도 130자 남짓 — `message`(255) 안에 들어옴을 계산으로 확인 |
| 알림이 갑자기 많아짐 | 벨은 여전히 전체 목록을 한 번에 불러온다 — 개수 제한/더보기는 실사용을 보고 판단하기로 남겨둠 |

### 테스트

`NotificationTypesFlowTest` 10케이스. **"알림이 생겼다"가 아니라 "누구에게 생겼는지"를 단언한다** — 수신자 오배정(예: 문의 답변 알림이 답변한 판매자 자신에게 가는 것)이 이 기능의 핵심 리스크이기 때문. 발행 코드를 일부러 제거해 실제로 실패하는 것까지 역검증했다.

`@Transactional`을 붙이면 안 된다 — 원본 트랜잭션이 커밋되지 않아 AFTER_COMMIT 리스너가 아예 실행되지 않는다. 실제로 커밋하고 `@AfterEach`에서 직접 지운다.

## 배운 것

- **AFTER_COMMIT + REQUIRES_NEW는 커넥션을 2개 잡는다.** 알림처럼 "본 작업 뒤에 곁들이는 쓰기"를 붙일 때 동기로 두면 동시성 하에서 풀을 고갈시킨다. 이 조합을 쓸 땐 `@Async`가 기본값이어야 한다.
- **깨진 테스트를 고치는 방향이 두 가지였다.** 대부분은 "이 테스트는 알림이 관심사가 아니니 목으로 끊는다"가 맞았지만, 커넥션 고갈을 잡아준 테스트만은 목으로 막으면 안 됐다 — 그게 유일한 회귀 감지 장치이기 때문. 실패한 테스트를 기계적으로 통과시키는 것과 실패가 알려준 사실을 지키는 것은 다르다.
- 로컬 MySQL 잔여 데이터로 실패가 9건까지 번졌다. 실패한 실행이 정리를 못 끝내면 다음 실행이 오염된다 — 원인을 고친 뒤엔 DB를 비우고 다시 재야 진짜 결과가 보인다.
