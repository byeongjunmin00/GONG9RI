# 알림 목록 페이지네이션 + 정확한 안읽음 개수 (notification/refund-alert)

담당: 민병준
대상 개념/기능: `notification/refund-alert` (기존 기능 확장)

## 배경 / 요구

알림 종류를 8종으로 늘리고 나서(`changes/003`) 남겨둔 후속이다. 헤더 벨이 **알림 전체 목록을 한 번에 불러와 전부 렌더링**한다 — 알림이 사실상 하나(환불)뿐일 땐 문제가 없었지만, 이제 결제·문의·리뷰·공구팀 성사까지 쌓이므로 목록이 무한정 길어진다.

사용자와 두 가지를 확정했다: 벨 안에 **"더 보기"**를 두고, **안읽음 개수는 목록 응답에 함께** 내린다.

## 무엇을 (범위)

### 1) 목록 페이지네이션

`GET /api/{buyer,seller}/mypage/notifications`에 페이지 파라미터를 받아 최신순으로 잘라서 내린다. 프론트는 벨을 열었을 때 첫 페이지만 받고, 맨 아래 "더 보기"로 다음 페이지를 이어붙인다.

**오래된 알림을 볼 곳이 벨 드롭다운밖에 없다**는 점이 이 선택의 근거다 — 마이페이지에는 알림 UI가 아예 없어서(헤더 스크립트만 로드한다), 목록을 그냥 N개로 자르면 이전 알림에 접근할 방법이 완전히 사라진다. 알림 전용 페이지를 새로 만드는 것보다 벨 안에서 이어보는 쪽이 스코프가 작아 이 방향으로 정했다.

### 2) 안읽음 개수를 서버가 센다

**이게 없으면 페이지네이션이 곧 버그가 된다.** 지금 뱃지 숫자는 프론트가 받아온 목록에서 직접 센다(`notifications.filter(n => !n.isRead).length`). 목록을 20개로 자르면 안읽음이 30개여도 최대 20으로만 세고, 그 20개를 읽는 순간 뱃지가 0이 되지만 실제로는 10개가 남는다.

그래서 안읽음 개수는 **잘린 목록과 무관하게** 서버가 세서 응답에 담는다. 응답 형태가 배열에서 객체로 바뀌는 **깨는 변경**이지만, 이 엔드포인트를 쓰는 곳이 헤더 벨 하나뿐임을 확인했다(`grep` 전수 확인 — 마이페이지 화면에는 알림 UI 없음).

### 스코프 밖

- 알림 전용 페이지 신설 — 벨 안 "더 보기"로 대체.
- 무한 스크롤 — 기존 상품 목록이 쓰는 "더 보기" 버튼 패턴을 그대로 따른다(일관성).
- 알림 삭제 / 오래된 알림 자동 정리 — 알림은 이력 보존이 원칙이라 현재 하드 삭제 자체가 없다.

## 어떻게 (접근/설계 방향)

- **응답 계약을 바꾼다.** 목록 응답이 `{ 안읽음개수, 전체개수, 다음페이지여부, 알림목록[] }` 형태가 된다. 정확한 필드명·기본 페이지 크기는 `docs/api/mypage.md`에 계약으로 확정한다.
- **안읽음 개수는 조회 쿼리로 직접 센다** — 목록을 받아 세는 방식이면 페이지네이션과 동시에 성립할 수 없다.
- **프론트는 페이지를 이어붙인다.** 이미 불러온 목록을 로컬에서 갱신하는 기존 원칙(읽음 처리 시 재호출하지 않음)은 유지하되, 읽음 처리로 안읽음 개수가 바뀌는 것은 로컬에서 함께 반영한다.
- 마지막 페이지에 도달하면 "더 보기"를 숨긴다.

## 통과(평가) 기준

- `./gradlew test` 전체 통과.
- **안읽음이 페이지 크기보다 많을 때**, 첫 페이지만 읽어도 뱃지 숫자가 실제 안읽음 개수와 일치한다(이번 변경의 핵심 — 이걸 검증하지 않으면 페이지네이션이 버그를 만든다).
- 다음 페이지를 요청하면 이전 페이지와 겹치지 않는 더 오래된 알림이 온다.
- 마지막 페이지에서는 "다음 있음"이 거짓이다.
- 본인 알림만 보이는 기존 스코핑, 반대 역할 403, 비로그인 401, 읽음 처리(개별/전체)에 회귀가 없다.
- 프로덕션 배포 후 실제 알림을 만들어 벨에서 확인.

## 실행 결과

계획대로 구현하고 **382케이스 전부 통과**(기존 379 + 신규 3).

### 계약 변경

`GET /api/{buyer,seller}/mypage/notifications?page=0&size=20`

```json
{
  "unreadCount": 5,
  "totalCount": 25,
  "hasNext": true,
  "notifications": [ ... ]
}
```

기본 페이지 크기 20. 배열 → 객체로 바뀌는 깨는 변경이지만, 이 엔드포인트 사용처가 헤더 벨 하나뿐임을 전수 확인 후 진행했다.

### 핵심 검증 — 로컬 실서버 실측

실제 계정을 만들고 알림 25건을 심은 뒤, **1페이지(20건)만 전부 읽음 처리**하고 응답을 확인했다:

| 확인 | 값 |
|---|---|
| 1페이지 안의 안 읽은 알림 | **0** |
| 서버가 준 `unreadCount` | **5** ← 안 불러온 2페이지까지 세서 정확 |
| 2페이지의 실제 안 읽은 알림 | **5** |

**옛날 방식(프론트가 받아온 목록에서 세기)이었으면 뱃지가 0으로 사라지고 5건이 유령처럼 남았을 상황**이다. 이게 이 변경에서 `unreadCount`를 서버가 세도록 한 이유 그 자체다.

이어서 페이지 경계도 실측했다 — 1페이지 20건/`hasNext=true`, 2페이지 5건/`hasNext=false`, 두 페이지가 겹치지 않음. "모두 읽음"은 아직 안 불러온 페이지의 알림까지 0으로 만든다.

테스트로도 같은 것을 고정했다(`size=2`로 줄여 목록은 잘리지만 `unreadCount`는 5로 정확한지, 마지막 페이지 `hasNext=false`, 모두읽음 후 0).

### 검증 중 겪은 것 — 앱 버그가 아니었던 실패

읽음 처리 20건이 전부 안 먹는 것처럼 보여 잠깐 앱 버그를 의심했는데, 실제 원인은 **zsh가 따옴표 없는 변수를 자동으로 단어 분리하지 않는다**는 쉘 동작이었다. id 20개가 통째로 한 토큰이 되어 잘못된 URL로 요청이 나갔고(`HTTP=000`), 개별 호출은 처음부터 정상이었다. 응답 코드를 직접 찍어보고 나서야 드러났다 — **"실패했다"를 곧바로 앱 결함으로 옮기지 않고 요청이 실제로 어떻게 나갔는지부터 본 게 맞았다.**

## 리스크 / 전제

- **응답 형태가 바뀌는 깨는 변경**이다. 사용처가 헤더 벨 하나뿐임을 확인했지만, 배포 순간 브라우저에 캐시된 옛 JS가 남아있으면 잠시 알림 목록이 안 뜰 수 있다(정적 자산 캐시 10분). 기능 자체가 깨지는 건 아니고 새로고침으로 해소된다.
- **정렬·조회 인덱스**: `notification`은 현재 `member_id` 인덱스만 있다. 최신순 페이지 조회가 잦아지므로 `(member_id, created_at)` 복합 인덱스가 이론적으로 유리하지만, **이번엔 추가하지 않았다** — 한 회원의 알림 건수가 인덱스 차이를 체감할 규모가 아니고(수십 건), 근거 없는 인덱스 추가는 쓰기 비용만 늘린다. 실제로 느려지는 게 관측되면 그때 `EXPLAIN`으로 근거를 만들고 추가한다(성능 개선은 실측 후 판단한다는 이 프로젝트의 기존 방침과 동일).
- 알림 생성이 `@Async`라 방금 만든 알림이 목록에 즉시 안 보일 수 있다(기존과 동일, 이번 변경과 무관).
- 로컬 검증에 MySQL + Redis 가동 필요.
- `docs/dev/ongoing/` 확인 결과 팀원이 같은 영역을 작업 중이지 않다.
