# 개발 로그 가이드 (logs-guide)

개발 **실행 이력·증거**를 `docs/logs/`에 남기는 방법이다.
로그는 두 역할을 한다:
1. **피드백 센서** — 에이전트가 이걸 읽고 다음 시도(루프)를 결정한다.
2. **증거·감사** — 사람이 "실제로 이렇게 돌아갔다"를 확인한다.

> 다른 문서와의 구분: `changes/`·`design.md`는 **스펙(계획·현재상태)**, `logs/`는 **실행 증거(raw 이력)**.
> 서로 안 겹친다.

## 위치 & 이름

```
docs/logs/{개념}/{기능}/00X-{작업}.md      예: docs/logs/team/join/001-join.md
```

- changes/의 작업과 **같은 번호**로 대응시킨다 (`changes/001-join.md` ↔ `logs/…/001-join.md`).

## 무엇을 기록하나

- **성공·실패 매 시도를 모두** 기록한다 (append-only). 실패를 빼면 에이전트가 같은 실수를 반복한다.
- 각 기록은 **고신호 요약**으로 남긴다. 원시 로그 통째 덤프 금지 (노이즈 → 판단 방해 + 컨텍스트 낭비).
- **무거운 산출물**(테스트 HTML 리포트, 부하테스트 원본)은 `build/`·별도 산출물 폴더에 두고, 로그엔 **요약 + 링크**만.

### 백엔드 증거 (프론트의 스크린샷 대응)

- ⭐ **API 요청/응답 샘플** — "엔드포인트가 실제로 이렇게 응답" (가장 핵심 증거)
- **테스트 결과 요약** — 통과/실패 + 실패 원인
- (선택) DB before/after 샘플, 쿼리 수·응답시간(N+1·성능), 동시 요청 시나리오 결과(정원 초과 방지 등)

## 로그 템플릿 (append-only)

```markdown
# 001-join — 공구팀 참가하기 (로그)

## Attempt 1 — 2026-07-24  ❌ FAIL
- 시도: 공구팀 참가 API 구현
- 결과: 동시 참가 테스트에서 정원(max_participants) 초과 발생
- 원인: current_count 갱신에 동시성 제어 미적용
- 다음: 락 방식 재계획 필요 (Plan으로 회귀)

## Attempt 2 — 2026-07-24  ✅ PASS
- 시도: 비관적 락 적용해 current_count 갱신
- 결과: `./gradlew test --tests "*TeamJoin*"` 전체 통과
- 증거(API 샘플):
  - `POST /api/group-buy-teams/1/join` → `200 {"teamId":1,"currentCount":3,...}`
  - 정원 초과 시 `POST /api/group-buy-teams/1/join` → `409 {"code":"TEAM_FULL","message":"..."}`
```

## 누가 기록하나

한 Attempt는 두 부분이고, 각 단계가 **자기가 아는 부분**을 기록한다 (순차 실행이라 충돌 없음):

- **Generator**: `시도` — 무엇을·어떤 접근으로 구현했는가 (자기가 한 일을 firsthand로 기록).
- **Evaluator**: `결과`·`원인`·`증거` — 테스트 통과/실패, API 샘플 (실행 결과를 append).

## 워크플로우 연결

- 재시도(루프) 시 **다음 generator는 fresh 컨텍스트**라 이전 시도를 모른다 →
  **로그를 먼저 읽어** 같은 접근을 반복하지 않는다. (그래서 generator가 자기 `시도`를 남겨야 한다.)
- (지속 기억: 세션이 바뀌거나 컨텍스트가 압축돼도 이 로그가 시도 이력을 보존한다.)
