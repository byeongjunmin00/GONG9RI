# Plan 가이드 (plan-guide)

실행 흐름의 **Plan(계획) 단계**에서 이 문서를 참고한다.
Plan의 목표: 코드를 만들기 전에 **무엇을·어떻게·어떻게 검증할지**를 문서로 확정하고 사람의 승인을 받는 것.

## 계획 전에 먼저 읽고 확인할 것

- **관련 `design.md`** — 대상 개념/기능의 현재 상태를 파악한다 (`docs/dev/{개념}/{기능}/design.md`).
- **관련 정책** — 이 작업이 걸리는 비즈니스 규칙을 확인한다 (`docs/policy/`).
- **`docs/dev/ongoing/`** — 진행 중인 작업과 **중복·충돌**이 없는지 본다 (2인 팀이라 특히 중요 — 팀원이 같은 영역 작업 중일 수 있다).
- **영향 범위** — 바뀔 파일/계층(controller·service·repository·entity·dto)을 식별한다.

## 계획에 담을 것

- **무엇을**: 변경 대상 (기능·파일·영역)
- **어떻게**: **접근/설계 방향**만 (필요하면 정책 참조). ⚠️ 구현 메커니즘이 아니다 — 아래 "고도(altitude) 경계" 참고.
- **통과(평가) 기준**: 어떤 테스트/확인으로 완료를 판정할지 미리 정한다
- **리스크/전제**: DB 가동 필요, 동시성 이슈 해당 여부 등 전제·리스크

## 고도(altitude) 경계 — Plan은 어디까지 정하나

Plan은 코드를 **읽어도** 되지만(영향 범위·리스크 파악용), 코드레벨을 **규정하지는 않는다**.
구체 구현은 Generate의 몫이다. 이 선을 넘으면 Plan/Generate 경계가 무너지고, Bash 없는 planner가
검증 못 하는 것을 처방하게 된다.

| Plan이 정한다 (✅) | Generate가 정한다 (❌ Plan에 쓰지 말 것) |
|---|---|
| API/DB **계약**(`docs/api/`·`docs/db/`) | 애노테이션·라이브러리 API 선택 (`@NotBlank`, `@Valid` 등) |
| 영향 **계층** 목록 (controller·service·…) | 계층 **내부** 구현 배치 (어느 검증을 DTO/service 어디에 둘지) |
| **접근/설계 방향** ("정원 초과는 동시 접근 제어가 필요하다") | 구체 **락 방식**·설정값·의존성 처방 (낙관적/비관적 락, `ddl-auto=update` 등) |
| 통과(평가) 기준 | 클래스 내부 로직·정확한 문자열/코드값 |
| **리스크·전제**(사실만 기술) | 그 리스크의 **해결책**(해결은 Generate가 결정) |

- 전제는 **리스크로 "알리는" 데서 멈춘다**. 예: "공구팀 참가는 동시에 여러 요청이 들어올 수 있어 `current_count` 정합성 보장이 필요하다(현재 락 미적용)" ✅
  → "이 경우 비관적 락을 걸어라" ❌ (해결책 처방 = Generate)

## 원칙

- **애매하면 추측하지 말고 사용자에게 질문**한다. 빈틈 있는 계획으로 넘어가지 않는다.
- 계획 범위를 벗어나는 작업을 임의로 넓히지 않는다.
- 계획 없이 바로 코드를 생성하지 않는다.

## Plan의 산출물

- Plan은 **`docs/dev/ongoing/{작업}.md`** 개발문서를 만드는 것으로 이어진다.
  (문서 작성법·필드·템플릿은 `docs/dev-doc-guide.md` 참고)
- 필요하면 **API 명세(`docs/api/`)·테이블 명세(`docs/db/`)도 이 단계에서 작성**한다.
  (generator는 이 명세대로 코드만 구현한다.)
- 위 문서들이 곧 **휴먼 게이트에서 승인받을 대상**이다.

## 승인 후

- 승인되면 Generate로 넘어간다. 승인 전에는 파일을 수정/생성하지 않는다. (Claude Code는 Plan Mode로 이 관문을 강제)
